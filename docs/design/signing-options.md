## 一、为什么必须有固定签名

Android 要求：同一个 `applicationId`（`dev.sopho.suofei`）的后续版本，**必须用同一个密钥签名**，否则系统拒绝覆盖安装。不同签名时用户只能**先卸载**——而卸载会清掉应用私有目录，也就是**已下载的内容快照会一起消失**（不影响 APK 内置内容，用户会退回内置那一版）。

对照现在：APK 是 **debug 签名**（`CN=Android Debug`），**不能用于正式发布**——所有本地构建、验收都用它，这是刻意的。

## 二、一个关键事实：现在选，代价为零

我们**还没有对外发布过任何版本**，也没有任何人装过。也就是说：现在无论选哪种方式、甚至换 `applicationId`，都**不会影响任何已存在的用户**。这是唯一一次能自由选择的机会；一旦首次发布，签名就成了**永久约束**（密钥丢失 = 已装用户永远无法升级）。

## 三、三个选项与代价

| 选项 | 做法 | 好处 | 代价 |
|---|---|---|---|
| ① **只在本机保存** | 密钥文件放本机（仓库外），口令由用户记住/放密码管理器 | 最简单、完全离线、不外传 | 换电脑、硬盘坏、口令忘记 ⇒ **密钥丢失 = 已装用户无法升级**（只能让他们卸载重装）。建议至少两处离线备份 |
| ② **放 GitHub Actions secrets** | 密钥 base64 进 secrets，tag 推送时由 CI 签名构建 | tag → 自动产出**已签名**的 APK，不必在本机手动出包 | 需要先建仓库并配置 secrets（因此也牵出「建仓」这个对外动作）；密钥进入云端（加密存储，但仍属「多一处副本」）；要额外注意 workflow 权限 |
| ③ **现在不决定** | 继续用 debug 签名做本地验收，等真发布前再生成 | 不引入任何密钥管理负担 | 发布前才第一次验证「正式签名能不能装配、`.apk` 能不能被 `apksigner` 验过」；风险不大但属于「把未知留到最后」 |

**我的建议**：先做一次**与你的正式密钥无关**的演练——① 生成一个**一次性的测试密钥**，② 跑 `assembleRelease`，③ 用 `apksigner verify` 与 `aapt2 dump badging` 证明「正式签名的包能构建、能验过」，④ **立刻删掉这个测试密钥**并写明它没用过、也不会用于发布。这一步能把「正式发布时的签名环节」变成已知，且**不涉及你的任何密钥**（仍需你点头，因为它会生成密钥文件）。
此后正式密钥选 ① 还是 ②，可以在建仓时一起定。
