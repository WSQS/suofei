## IF-1 一诗一 Markdown 的字段与 ID 规则

**它决定什么**：内容在仓库里怎么存。这是你以后自己加诗、改字、写笔记时直接打交道的东西。

**原样**（`content/poems/gushi-shijiu-shou-01.md` 的骨架，示意）：

```markdown
---
id: gushi-shijiu-shou-01
title: 行行重行行
author: 佚名
dynasty: 汉
dynastyOrder: 100
era: 东汉末
genre: 五言古诗
source: 《文选》卷二十九（具体校录来源与访问日期由内容线填）
variants:
  - text: （异文示例，内容线核对后填入）
    note: （据某本，具体由内容线填）
notes: |
  （这里是你自己的笔记，Markdown 文本。没写就整行省略。）
---

行行重行行，与君生别离。
相去万余里，各在天一涯。
（空行表示分段）
胡马依北风，越鸟巢南枝。
```

**为什么这样定**

1. **一诗一文件**：改一首诗只动一个文件，diff 干净；多条线并行写内容时不会互相覆盖。
2. **用 front matter 而不是一个总表**：你手写、手改最省事；不用同时维护「总表」和「正文」两处。
3. **`notes` 单独一个字段**：你的笔记和原文**永不混在一起**，也永远不会被编译工具改写你的字。这是 `CONTEXT.md`「agent 不代写第一人称内容」在格式上的落实。
4. **`source` 必填、`variants` 可选**：`CONTEXT.md` 要求「初始诗只取已核来源的原文」「异文不混入正文」。异文记在字段里、正文只留定本，就是这条的落实。
5. **id 形如 `gushi-shijiu-shou-01`**：带了来源集合名，以后加别的集合不会撞号。

**其他做法的代价**

| 其他做法 | 代价 |
|---|---|
| 19 首放在一个 JSON/YAML 总表里 | 改一首诗的 diff 和其他诗混在一起；两个人同时改会冲突 |
| 用诗名当文件名（`行行重行行.md`） | 中文文件名在 URL、跨系统、压缩包里都要处理编码；改了标题要改引用 |
| id 用纯数字 `1..19` | 以后加第二个集合时会撞号，也无法一眼看出它属于哪组 |
| 用 CSV/Excel 维护 | 分行、空行、长笔记都表达不了 |

**一个附带的小选择**（我的建议：保持现状）：作者佚名时写 `author: 佚名`，而不是留空 + 客户端显示「佚名」。
理由：留空意味着每个用到作者的地方（显示、排序、搜索）都要特判一次空值；写成显式值更简单，且「佚名」本身是数据的一部分。代价：「佚名」三个字会出现在数据里，将来若想改成别的说法（如「无名氏」）要改 19 个文件——但现在改也只是一次批量替换。

## IF-2 `dist/content.json` 的结构

**它决定什么**：Android 与 Web **唯一**的读取入口。两端只认这个文件。

**原样**（示意）

```json
{
  "formatVersion": 1,
  "contentVersion": "2026.10.14.1",
  "generatedAt": "2026-10-14T12:00:00Z",
  "dynasties": [{ "key": "han", "label": "汉", "order": 100 }],
  "poems": [
    {
      "id": "gushi-shijiu-shou-01",
      "title": "行行重行行",
      "author": "佚名",
      "dynastyKey": "han",
      "dynastyLabel": "汉",
      "dynastyOrder": 100,
      "era": "东汉末",
      "genre": "五言古诗",
      "source": "…",
      "variants": [],
      "stanzas": [["行行重行行，与君生别离。", "相去万余里，各在天一涯。"]],
      "notes": null
    }
  ]
}
```

**为什么这样定**

1. **只有一个文件**：离线语义变得极简单——「整个文件完整下载 + 校验通过 = 内容就是完整的新版」。原子切换、失败保留旧版都好实现，也不用担心「下了一半」。
2. **`dynasties[]` 只列有内容的组**：组的顺序与标签来自数据本身，客户端不硬编码。以后加一首唐诗，组会自动出现，两端代码不用动。
3. **`formatVersion`（结构版本）与 `contentVersion`（内容版本）分开**：应用升级和内容升级互不牵连。内容加了首诗，不用发新版 App；结构变了，旧客户端知道要保留旧内容而不是去解析它。
4. **`dynastyKey` + `dynastyOrder` 同时存在**：前者给程序用（分组归并），后者给排序用（汉→唐的时间轴顺序），`dynastyLabel` 给显示用。三者都是为了让客户端**不需要内置一张朝代表**。

**其他做法的代价**

| 其他做法 | 代价 |
|---|---|
| 每首诗一个 JSON，按需加载 | 首屏快，但「完整离线」要下 19 个文件，原子切换变复杂（要做清单+校验+逐个替换）。本项目只有 19 首、未来也是小体量，不值得 |
| 把 Markdown 原样塞进 JSON，客户端自己解析 | Web 要引 Markdown 解析器；两端对分行、空行、笔记的处理容易漂 |
| 两端各自去解析 `content/poems/*.md` | 客户端要背 YAML 解析器；编译期校验（重复 id、缺字段）就没人做了 |

**附带说明**：`notes` 为 `null` 或 Markdown 字符串。`CONTEXT.md` 说第一版没有独立注释界面、笔记按需展开——所以笔记就是**一段文本**，不作为结构化数据。这是有意的简化。

## IF-3 分段表示（你阅读时直接看得到的那一条）

**它决定什么**：正文在网上怎么断行、怎么分段。

**原样**：`stanzas` 是**两层的数组**——外层每项是一段，内层每项是一行。

```json
"stanzas": [
  ["行行重行行，与君生别离。", "相去万余里，各在天一涯。"],
  ["胡马依北风，越鸟巢南枝。"]
]
```

对应屏幕上的样子：

```
行行重行行，与君生别离。
相去万余里，各在天一涯。

胡马依北风，越鸟巢南枝。
```

**为什么这样定**

1. **每印刷行 = 一行**（十字两读一行，如「行行重行行，与君生别离。」）：这是《文选》纸本的排印方式，也是古诗十九首通行的读法。
2. **空行 = 段边界**，并且用**结构**表达，而不是靠字符串里的 `\n`：
   - Web 的 HTML 会把连续空白折叠，`\n` 不会自动变成换行，要用 `white-space` 等 CSS 手段；
   - Compose 的文本布局规则又不一样。
   - 如果只存一个大字符串，两端都要自己处理空白，**很容易一端对、一端错**。存成两层数组后，两端只要「一段一个块、一行一个元素」就不会漂。
3. **不丢空行信息**：《古诗十九首》多数版本是连续排印，但以后的诗（如长诗、分节明显的作品）会用到分段。现在不表达，以后要补就得改结构。

**其他做法的代价**

| 其他做法 | 代价 |
|---|---|
| 一句一行（`行行重行行，` / `与君生别离。`） | 视觉更疏、一屏装不下、与原书排印不符 |
| 整首一个字符串（`"行行重行行，与君生别离。\n相去万余里，…"`） | 依赖两端各自的空白处理，最容易出现「同一条内容两端不一样」 |
| 只存行、不存段 | 丢失分段信息，以后想恢复必须改结构重编译 |

**可后加项（我不打算现在做，但结构上不挡）**：若以后想要「一句一行」的疏朗排版，因为中文标点（，。）天然可切分，可以在渲染时按标点切，不必改数据结构。所以这条不构成现在必须决定的事——除非你对默认排印方式本身有意见。

## IF-4 排序规则与「佚名排最后」★ 这一条需要你拍板

**它决定什么**：目录里诗的先后顺序——你翻开应用第一眼看到的东西。

**原样（契约 v0 的写法）**：编译期算好排序键，用拼音排序；**佚名/未知作者在该组内排最后**。

这个规则来自 `CONTEXT.md` 的原话：「组内按作者/诗名自动排序」。问题是：**《古诗十九首》19 首的作者全是「佚名」**，于是「先按作者、再按诗名」实际退化成「按诗题拼音排序」，而**《文选》里这 19 首的次序本身是有讲究的、是这组诗的一部分**。我把真实后果算了出来（本机 `Intl.Collator('zh-Hans-CN-u-co-pinyin')` 实测）：

| 原次序（《文选》） | 拼音自动排序后会变成 |
|---|---|
| 1 行行重行行 | 1 东城高且长 |
| 2 青青河畔草 | 2 回车驾言迈 |
| 3 青青陵上柏 | 3 今日良宴会 |
| … | … |
| 19 明月何皎皎 | 19 **行行重行行** |

**19 首里有 18 首位置发生变化**，最刺眼的是：**「行行重行行」从第一首掉到最后一首**。

**两种做法的代价**

| 做法 | 好处 | 代价 |
|---|---|---|
| **A 保留《文选》次序** | 与纸本、与通行认知一致；「第一首是行行重行行」符合直觉 | 需要给每首一个显式次序字段（如 `orderInSource`）；`CONTEXT.md` 说的「自动排序」在这组上不生效（但它在「唐」这类作者多样的组里仍然生效） |
| **B 拼音自动排序** | 完全照 `CONTEXT.md` 字面；不需要额外字段；作者多起来后查找更容易 | 十九首的传统次序被打乱，「行行重行行」变最后一首 |
| **C 两者都保留** | 目录默认按原次序，另给一个「按诗名排序」的开关 | 多一个字段、多一个交互开关、两端各做一遍 |

**我的建议是 A**：内容规模小、作者几乎全佚名，自动排序在这组上带来的价值很小，而丢掉传统次序是**看得见的损失**。`CONTEXT.md` 里「组内按作者/诗名自动排序」的本意是「不要让作者顺序随机/手工维护」，而 A 用**编译期算好的显式次序**满足了同样的目的（仍然是自动的、不用手工排目录），只是次序来源换成了底本。

## IF-9 目录与模块边界

**它决定什么**：东西放在哪里——影响以后每条线改哪、以及仓库看起来是否清楚。

**原样与理由**

| 目录 | 放什么 | 为什么这样分 |
|---|---|---|
| `content/poems/` | 一诗一 Markdown | 你手写的源头，进版本库 |
| `dist/` | 编译产物 `content.json` | 产物不进版本库（已 gitignore），避免「产物和源码都改了但只提交一个」 |
| `tools/`、`schema/`、`tests/` | 编译脚本、JSON Schema、测试 | 内容流水线独立，和两端代码分开 |
| `android/`、`web/` | 两端工程 | 各自构建、各自发布，互不干扰 |
| `prototype/` | 原型 | 明确是设计探索，不是产品代码，评审后可丢 |
| `docs/` | 契约、状态、评审、来源记录 | 文档单一入口 |

**其他做法的代价**：把 Android 与 Web 塞进一个多模块工程——构建链更重、但两端并不共享代码（`CONTEXT.md` 已定「不要求两端都使用 Web 渲染」），不值得。
