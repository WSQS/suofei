# 原型（工作线 B）—— 索斐 · 可运行阅读原型

一次性的**设计探索**，用来回答「视觉与交互该长什么样」；不是最终实现，也不代表 Android/Web 已有代码。
纯静态 HTML/CSS/JS：不引框架、不引构建工具、不引外链 CDN、不联网取字体（中文全用系统字体）。

## 怎么打开

```bash
# 方式 1：直接双击（file:// 打开，自动用内置 fixture 数据）
prototype/index.html

# 方式 2：起本地服务（推荐，能走 http，两种数据源都能看）
cd prototype && node tools/serve.mjs        # → http://127.0.0.1:8137/
# 或者： cd prototype && npx serve

# 方式 3：真的走编译产物（工作线 C 产出 dist/content.json 之后，从仓库根目录）
cd <仓库根> && npx serve                    # 然后打开 http://127.0.0.1:3000/prototype/
```

数据来源优先级（原型自己判断并在界面上写明用了哪个）：

| 情况 | 结果 |
|---|---|
| `../dist/content.json` 存在且形状正确 | 用编译产物；页头计数显示 `数据：dist/content.json`，**没有**示例数据提示条 |
| 读不到（file:// 会被 CORS 挡、或文件还没生成） | 回退到内置 fixture，页头显示 `数据：fixture（示例数据）` 并挂一条提示条 |
| URL 带 `?data=fixture` | 强制 fixture |
| URL 带 `?dist=别的.json` | 读指定的同形状 JSON（`data/sample-content.json` 就是为验证这条分支准备的样本） |

其它可用 URL 参数：`?theme=paper|clean|tech`（也可在界面上点「视觉」三个按钮切）、`?debug=1`（页脚打印实测尺寸）。
路由是 hash：`#/`（目录）、`#/g/<组>`、`#/p/<诗 id>`，可以直接贴链接给人看某一页。

## 数据是占位的，别当正文用

- 全部诗文本、笔记都在 `js/fixture-data.js` 里，标了 `fixture: true`，每首的 `source` 写的是
  **「fixture 占位文本，来源待内容线（A）核对」**；界面上有黄条提示，诗页页脚也再写一次。
- 界面上那条带 **「测试数据」** 徽标的笔记是**造出来的测试数据**，不是用户真实笔记 ——
  它只用来观察「长笔记折叠/展开」的表现（折叠态 / 展开态截图见下）。
- 正文里出现的人物、异文登记都不是校对结论；`variants` 只展示**不进正文**的异文，是否符合底本由 A 线定。
- JSON 结构严格按 `docs/design/content-contract.md` 的 `content.json` 形状（`dynasties` / `poems` /
  `stanzas` / `notes` / `variants`），这样原型不会长出一个和数据契约不同的形状。

## 三个视觉方向

三个方向**共用同一份数据、同一套交互和同一份布局代码**（`css/base.css`），只换 CSS 变量主题：

| 方向 | 取向 | 代价 / 风险 |
|---|---|---|
| **A 宣纸**（`theme-paper`） | 暖米底、宋体正文＋楷体诗题、细线、直角、几乎无阴影。界面尽量退到纸的后面 | 观感偏「旧」；UI 文字（计数、标签、搜索结果）也跟着收敛，信息密度最低；暖底 + 衬线在小字号下不如无衬线清楚 |
| **B 清爽**（`theme-clean`） | 白底、系统无衬线、卡片与柔和阴影、蓝色强调、圆角 | 气质偏「应用」不偏「书」；正文与 UI 同族无衬线，长诗呼吸感弱于 A；阴影/圆角用多了会抢注意力 |
| **C 静默终端**（`theme-tech`） | 深墨底 + 低饱和青灰、发丝线、等宽数字与 `[n]` 计数、极淡网格。**不用霓虹、不用发光、不加动效** | 三个里最不像「书」；深底长文更累眼；异文小字这类印刷习惯在深底上更弱。留作横向对照项 |

我倾向 **A 宣纸** 作为「读诗」的主方向：它把视觉权重放在正文（衬线、行距 2.05、字距 5%）上，
诗题用楷体与正文拉开层次，界面元素（组、计数、按钮）都退成细线，读的时候几乎没有东西在跟正文抢注意力。
B 的长处是「应用界面」那部分（分组计数、搜索结果、将来的更新提示）最清楚，如果要走 B，
建议把正文区单独调成衬线（相当于「B 的骨架 + A 的正文」），这是我更想听用户拍板的地方。
C 的科技感是靠**结构**（发丝线、等宽计数）而不是靠**光**做出来的，作为对照项成立，但我不建议拿它当读诗默认。

## 评审要点（每一条都能在截图里看到）

1. **首屏**：一眼能看出「5 组 / 10 首」，每个组行右侧是**该组首数**，上行是「组名 + 该组诗题预览」。
   组只显示有内容的组；`未详` 也是一个正常的组，不是错误状态。
2. **组内**：直接列「诗题 ＋ 作者」，没有作者页；排序是**组内先作者、再诗名，佚名排最后**
   （汉组三首全是佚名，所以按诗名拼音排：青青河畔草 / 涉江采芙蓉 / 行行重行行）。
   有笔记的诗在组内带一个 `笔记` 小标。
3. **诗页正文**：分行与分节**真实保留** —— 每一印刷行是独立 DOM 元素（`white-space: pre-wrap`），
   段间用一个段间距表达原来的空行（`行行重行行` 8 行 1 段 / `短歌行` 16 行 4 段，可直接对比）。
   不做两端对齐、不做标点悬挂，所以全角标点的位置不会忽左忽右。
4. **笔记按需展开**：默认折叠（诗页只露一行标题栏）；展开后才渲染内容；没笔记的诗显示
   「这首诗还没有笔记」的真实空状态，而不是藏起来。长笔记展开后是独立区域，不挤动诗题与正文。
5. **跨组搜索**：一个输入框搜「诗名 / 作者」，命中列表每条都带**所属时代 + 该组首数**徽标；
   搜 `佚名` 会跨「汉」和「未详」两组命中 4 首（v0 契约只要求子串匹配，拼音搜索未做）。
6. **来源与异文**：诗页页脚分两块，异文明确写「不进正文」，来源字段就是将来放底本说明的位置。
7. **三个方向横向对比**：截图里同一屏（首屏、同一首诗）三个方向各一张，便于比较语气差异。

## 工具与已知环境坑

- `tools/shot.mjs`：用 CDP（`Emulation.setDeviceMetricsOverride`）精确指定 CSS 宽高与 DPR 后截图。
  原因：本机旧式 `chrome --headless --screenshot --window-size=430,932` 实测窗口宽度有下限
  （`innerWidth` 仍是 484 CSS px），而截图只有 430px 宽 → 右侧内容被硬裁，看起来像原型溢出，**是假红**。
- `tools/shot.mjs` 会在截图后自检：页面没渲染、`uncaught` 异常、或 `--expect` 断言不满足时
  **以非 0 退出并打印页面报错**，不交空白图。（这套自检就是靠它抓到过一次 `ReferenceError` 白屏。）
- `tools/serve.mjs`：零依赖静态服务器（只为了不下载任何包也能验证 http 分支）。

## 已知未验证项（都没做，别当成已验证）

- **未在 Android WebView / 真机上验证**：字体、行距、密度、点击热区都只是桌面 Chromium 里的观感；
  本机模拟器有人在用，本轮不碰。
- **未验证真机字体**：宣纸方向依赖 `Songti SC / SimSun / KaiTi`，Android 侧不一定有这些字体，
  实际需要按平台各自决定衬线回退（这是选型问题，不是改 CSS 能解决的）。
- **未做无障碍检查**：没有跑对比度/读屏/键盘顺序检查（只顺手标了 `aria-expanded`、
  `aria-label` 等少量属性），组行/诗行的命中区大小、对比度都还没量过。
- **未做拼音搜索**：按 v0 契约只用子串匹配，`Intl.Collator('zh-Hans-CN-u-co-pinyin')` 只用于排序。
- **没有真实笔记**：长笔记是测试数据；真实笔记的 Markdown 复杂度（图片、表格、行内代码）没做，
  现在只渲染段落 / 引用 / 无序列表 / 粗体。
- **没有真实内容产物**：没读过 `dist/content.json`（C 线还没产出），只用手写同形状样本验证过读取分支。
- **未覆盖的交互**：更新提示与内容切换、书签、字号调节、深色跟随系统、两栏横屏，都不在本次原型里。
- **视觉未冻结**：本原型的三个月方向都是候选，等待用户拍板；不要据此写两端的最终样式。
