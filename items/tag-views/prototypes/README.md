# 多浏览视图（朝代 ／ 选本）—— 可操作原型 · 入口候选 A／B／C

> 父项：[`tag-views`](../item.md) ← [`content-tags`](../../content-tags/item.md)；语义边界见 [`tag-semantics`](../../tag-semantics/item.md)。
> **这一份是原型材料，不是产品实施、不是整页规格、不是发布。**
> 数据分两半：**诗的正文／作者／朝代／体裁／底本／详情＝真实内容（只读抄自 `content/poems/`）**；
> **「选本」与「诗 ↔ 选本」的归属＝夹具**（临时编造，只为把界面表达出来）。本目录不写 `content/`，不给真诗打标签。

## 1 · 怎么打开

- **直接双击** `q-tag-views.html` 即可（file:// 下可用；路由用 hash，不用 `pushState`，因为 file:// 下 `pushState` 会被拒）。
- 需要本地服务时（可选，随便一个静态服务器）：

```sh
cd items/tag-views/prototypes
uv run python -m http.server 8811          # 或：npx serve .
# 打开 http://127.0.0.1:8811/q-tag-views.html
```

⚠ 端口别用 7331／7321（本机有活实例）。

页面顶部那条**原型条**（青色虚线框）**不属于应用页面**：它标着「讨论原型 · 非产品实施 · 夹具数据」，并给出三个候选的切换按钮、当前视口宽、内容宽 C、以及 `scroll` 读数。下面 `.pg` 里的东西才是被评审的那一层。

## 4 · 故意未表达（诚实清单）

1. **系统返回（Android 返回键／手势）**：本原型只做了 **Web 侧**（页面「返回」＋浏览器后退，两者都验过）。Android 侧没实现也没验；只能说层级上「每层一个历史条目」可以对齐——**不算已验证**。
2. **跨重启／刷新记忆**：视图选择与滚动位置只在**当前页面内存**里保留；刷新回到候选的起点，不记得上次看的是「选本」。跨重启记忆从未定，本原型不假装有。
3. **真机／WebView／iOS**：只在无头 Chromium 上跑过；触摸手感、300ms 点击延迟、滚动惯性、安全区都没验。
4. **无障碍**：只写了基本的 `role=tablist/tab`＋`aria-selected`、`aria-expanded`、`role=menu/menuitemradio`；**没有**核键盘焦点顺序、没有 TalkBack 朗读核验、没有重新核对比度（用的是已选令牌）。
5. **同名不同选本**（tag-semantics §2.5）：界面**没有**表达区分方式（例如「唐诗三百首（蘅塘退士本）」）。选本行只有显示名，没有限定词——留给语义／字段侧定，本原型不擅自选一种。
6. **标签改名与稳定标识**（§2.6）：原型的选本显示名同时被当作唯一标识（夹具数组的 `id` 与显示名分开写，但界面上看不出差别）；没有演示「改显示名但归属不断」。
7. **多标签的上限／排序**（§2.1）：一首诗属于两个选本时有数据，但**界面不显示"这首诗属于哪些选本"**（选本页只单向从选本到诗）。要不要在诗页/诗目上显示归属标签，本原型没做。
8. **标签是否只承载选本**（§2.10，语义未定）：入口文案写的是「**选本**」，这是一个**候选命名**，不是已确认术语；若标签将来也承载主题／作者，这条文案要改。页面其余部分没有假设「只有选本」。
9. **其他浏览轴**：作者视图、体裁视图一律没做（本项只要「朝代 ＋ 标签」）。
10. **宽度只出了 320 与 430**：834／1180／横屏没出图（宽度口径本身是已选的，但本轮没在平板/桌面重新出图）。
11. **长题名折行、超长诗行按句读折行**：没放这类夹具，也没表达（已选规则在 `ui-poem`，本轮不重开）。
12. **关于页**：顶部「关于」是个不导航的控件（`title` 里写了「本原型不实现关于页」）；关于页不在本项范围。
13. **笔记／详情 Markdown 全子集**：详情只渲染了真实 `detail` 里出现的三种元素（`###` 小标题、`- ` 列表、段落与 `**粗体**`），不是通用 Markdown 渲染器；本库这些诗都没有笔记 ⇒ 笔记入口整块不存在（已选：无笔记隐藏）。

## 6 · 三个候选的代价对比

| | **A 顶部 tab**（朝代｜选本） | **B 顶部下拉**（浏览：朝代 ▾） | **C 独立页**（选本 ›） |
|---|---|---|---|
| 进入选本 | 切 tab → 选本列表 → 选本 | 展下拉 → 选本（少一次点击） | 目录顶部「选本 ›」→ 选本列表 → 选本 |
| 层级深度（到诗） | 3 屏：视图 → 选本 → 诗 | 2 屏：朝代 → 诗（选的直接是选本） | 4 屏：目录 → 选本列表 → 选本 → 诗 |
| 默认目录是否被改 | 顶部行多两个控件 | 顶部行只多一个控件 | **完全不变**，只多一个弱入口 |
| 「有哪些选本」可见 | **能**（一整页，能横向比较各选本已收录数） | **不能**（要展开菜单才知道） | **能** |
| 每个视图的滚动位置 | 各自记住（朝代／选本互不干扰） | 只有朝代有位置 | 三层各自记住 |
| 返回语义 | 选本页返回到「选本」tab | 选本页只能返回朝代（**没有"选本列表"这一层可回**，上下文丢一次） | 逐层返回，最长 |
| 扩展更多视图（作者/体裁…） | 顶部 tab 会变成一排，退化风险最高 | **最省**（菜单里加一项即可） | 每加一个轴＝再加一个入口页 |
| Android 返回键 | 2 次回目录 | 1 次回目录 | 3 次回目录 |
| 主要代价 | 顶部信息变多；「模式」状态需要用户记住 | 选本集合藏起来；首数只能塞进菜单行；返回丢上下文 | 点击链最长、弱入口容易被忽略、上一级要多按一次 |

**建议（供评审，不是已定）**：若只留一个，建议 **A**——它同时满足「默认视图不被挤掉」和「能切回」，而且把「本库已收录 N 首」放在一个可以**一眼比较**的列表页上（B 里这个数字只能挤在菜单行，C 里要多两次点击才看到）。若预期视图种类还会明显增长（作者、体裁…），则 B 的「一个入口」更稳，但需要另找一处让「有哪些选本」可见。C 适合将来确实是「每轴一层」的产品结构。
**可混搭**：A 的 tab ＋ C 的「选本列表页」是同一份列表（本原型里就是同一个渲染函数）；A 的 tab ＋ B 的菜单则不建议（两种切换语义并存会互相打脸）。
