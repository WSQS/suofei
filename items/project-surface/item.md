# 项：工作台迁移（`items/` 本身）

## 这一项存在的原因（**诚实交代**）

用户 **2026-10-15** 就拍板了：**按 `engineering-workflow` 的默认形状建完整 `items/<项>/item.md` 树**（选项原话含「含 `prototypes/`、`history/`；会先出现一批空壳，且要把现有材料搬过去」）。

**但这条决定当时没有被记进任何项目文件，也没有落地**——它只存在于会话记录里。直到用户 2026-10-15 追问「**为什么现在的组织方式还不是按 item 组织的？**」，才补上本目录。

**为什么会掉**（不是借口，是成因）：
- 我把分工写成「调度侧落骨架 → 我填 `item.md` → 调度侧补边」，然后**把它当成"等对方先动"的事**；
- 之后被 UI 与源文件格式的连续讨论推着走，**没有任何一份文件把它记成一条待办**（连一句话都没有）；
- ⇒ 于是它成了"**没人盯的工作项**"。而讽刺的是：**这正是 `items/` ＋ 依赖图这套东西存在的意义**——一个正式的图会把「用户已批准但未落地」标成一条硬边，然后它就一直看得见。**它的缺席，导致了它自己被遗忘。**
- 同类失败的第二次：第一次是「视觉方向批准了但没接线到实现」（已发布才发现）。

## 本轮补做了什么

- 建 `items/`：`graph.md`（项 ＋ 硬边 ＋ 开放区域）＋ 每个项一份 `item.md`（范围／当前理解／**采纳版本锚**／证据指针／开放区域／未表达的）。
- 采纳锚里**如实写明"当初是在什么材料上批准的"**（例如视觉方向是在**夹具数据＋拼音序**的截图上选定的）——这是以前最缺的一句话。

## 交付同步缺口与修正要求（用户本轮指出）

用户指出负责人有进展却没有主动同步给对话侧，导致用户反复询问才能得知材料已交付。实例如关于页去框版已合入 `d0ff5d4`，对话侧仍需手动读负责人会话才获取更新。**只写自己的最终回复、更新Git或status，不等于已通知对话侧**；用户不承担会话间搬运责任。

修正要求（已发负责人协调落实，不宣称自动化已验证）：

- 负责人在**材料交付/返修合入、当前路径变化、真实阻塞或状态显著变化**时，主动用 `session_send` 投递给对话侧 `e1d07e6c-f615-43b1-943c-a3325dd9cafa`；不能只在本会话回复或等待用户转告。
- 投递包含：变化及提交锚、**当前存在的路径**、已核/未核、继承与未表达范围、是否需要用户看什么、下一步及仍在跑的线。归档搬迁在同条中给新路径，避免旧链接。
- `notify:false` 可避免要求收件方落定后再反向唤醒发送方；但仍须检查本次投递的真实 `accepted/delivered` 回执。失败如实处理，不把已写摘要视为已送达。两边不以空确认制造互相唤醒循环。
- 对话侧收到后读回必要产物（视觉交付包括实际图，而非仅断言数量），更新自己维护的理解/采纳锚与路径，向用户给出有意义的新进展；没有新变化不重复刷状态、不重新询问已定方向。
- 此项是协作修正，不修改会话宿主/通知系统，不保证模型不运行时自行轮询。成效以实际主动投递及本侧接收验证，非口头约定即完成。
