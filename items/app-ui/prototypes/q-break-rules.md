## 3 · 已选规则怎么表达成一个**可核的算法**

本页把它写成一个**纯函数**（输入：文字 ＋ 容器可用宽 ＋ 逐字推进宽；输出：每一行文字），页面与自检各有一份**独立实现**：

```
k = 0
while k < n:
  ① 若 width(text[k..n]) ≤ W          → 整段作一行，结束          # 规则 1
  ② 取「放得下范围内最后那个可用句读」：
     p = max{ q : k < q ≤ n, text[q−1] ∈ 句读候选集, width(text[k..q]) ≤ W }
     （遍历到第一个超宽的 q 就停 —— 宽度对前缀单调 ⇒ 这就是「放得下范围内」）
  ③ 若 ② 找不到（＝无标点，或这个半句本身仍超宽）：
     p = max{ q : width(text[k..q]) ≤ W }                        # 在行尾按放得下的字符断
     再按规则 4 回退：若 text[p] 是收尾类 ⇒ p−1（前一字连标点一起下移）
                     否则若 text[p−1] 是开局类 ⇒ p−1（开局标点不留行尾）
  ④ 落成一行，k = p，回到 ①                                        # 余文续行
```

**「放得下」的判据**：`该段文字实测推进宽 ≤ 容器宽`（**等于也算放得下**）。
**宽度怎么量**：本页用一把 `width:max-content` 的**量宽台**（正文 `17px`／行高 `2`／字距 `0.045em`），**逐候选直接实测那一段的宽度**——不用「字位数 × 常数」估算。
本机实测：**一个全角字 17.765–17.766px**（＝ `17 + 0.045×17`；**8 个字实测 142.13px ⇒ ÷8 ＝ 17.77**）。
⚠ 单字的 `getBoundingClientRect` 会被 Chrome 舍入到 1/64px（本机量到 **17.75**，真值 17.765）⇒ 自检**不用单字量做依据**，改用「8 个字实测宽 ÷ 8」。

**所有窄／量测容器的宽度也是实测出来的**：`容器 ＝ 参考串实测宽 ＋ 0.05px`（0.05px 是避开 Chrome 1/64px 舍入边的余量），**不是** `N × 17.766`。本机实测：

| 档 | 参考串 | 容器宽 |
| --- | --- | --- |
| 5 个字宽 | `甲×5` | **88.88px** |
| 6 个字宽 | `甲×6` | **106.64px** |
| 8 个字宽 | `甲×8` | **142.18px** |
| 12 个字宽 | `甲×12` | **213.24px** |
| 规则 2 边界例的「恰好」 | `甲，乙；丙、丁。`（8 字） | **142.18px**（＝ 142.13 ＋ 0.05） |
| 规则 2 边界例的「差 1px」 | 上者 − 1px | **141.18px** |
| 混西文那一格 | 固定 78px | **78px**（**故意**落在西文串中间） |
| 开局标点那一格 | 固定 60px | **60px** |

## 6 · 实现代价（**如实**；含我选了哪条路）

**我选的路径：① 自己算断点 + 逐行 `span`（`display:block`）渲染。**
理由（技术上的最稳）：规则 2 的「**放得下范围内最后那个**」与规则 3 的「**退到行尾字符断 ＋ 禁则**」**都不是浏览器能替我们决定的事**；把每一行算出来、每行落成一个块，浏览器就**不再参与折行** —— 屏幕上哪一行是什么字**完全由规则决定**，这也正是本页能逐字断言的原因。

| # | 做法 | 代价 | 风险 |
| --- | --- | --- | --- |
| **①** | **逐行 `span`（本页采用）** | 渲染层要有一份「分行结果」；宽度／字号／字体一变就要**重算**；而且必须**自己把宽度量准**（本页用一把 `max-content` 量宽台逐候选实测） | 量宽台与真实排版若**不同源**（字体回退换了字面），断点会变；量不准就会出现溢出或留白 |
| ② | **分段块 ／ `<br>`**（只在句读处切段，段内交给浏览器） | 只能在**句读**处切 ⇒ 规则 3 的「按字符断 ＋ 禁则」**拿不到**（本页 R3B 窄容器那一档就做不到）；段内浏览器折出来的行宽**不受我们控制** | 逐字断言变弱；两端更容易不一致 |
| ③ | **读回浏览器断点后重排**（先让浏览器折、量出断点、再按它重排） | **必须等布局完成再量**，且要在 resize／字体加载后**重新量** | **它拿到的是浏览器的断点**：本页 R5 实测 ③ ＝ `甲乙丙丁戊，己庚`／`辛壬癸`（8／3）**≠** 规则给的 `甲乙丙丁戊，`／`己庚辛壬癸`（6／5）⇒ **再重排也变不出规则 2 的断点**；量测与重排之间还会跳一帧 |
| ④ | **纯 CSS** | —— | **做不到**：`line-break` 只有 `normal／strict／loose`（都是字位＋禁则），没有任何 CSS 属性表达「优先在标点后断」；`hanging-punctuation` 本机不支持（上一轮 `q-break` 已实测） |

**⚠ 两端必须同一规则。** 源 Markdown 不改、只在渲染层断 ⇒ **Web 与 Android（原生 Compose，不是 WebView）各做一次**实现。可以先共用的**不是渲染**，而是：

1. 一份**纯规则**（输入＝文字 ＋ 可用宽 ＋ 逐字推进宽；输出＝每行文字）——本页 §3 那个伪码就是它的规格；
2. 一张**断点测试表**（本页这些夹具 ＋ 期望的每一行文字 ＋ 期望断点位置），两端各自跑同一张表，**不一致就红**。

**本页做到与没做到的边界**：本页**只在渲染层**做了这件事，产物是**一个原型页面 ＋ 一份自检脚本**；它**没有**改动 Web／Android 的任何实现文件（`web/` 与 `android/` 里对「句读／断行／breakLines」是 **0 命中**）。
**Android（Compose）侧的断行实现不在本页范围** —— 那条独立存在，本页只在上面这张表里把它写成代价，**没有任何实现或验证**。

## 7 · 没表达什么、没验什么（诚实清单）

**本页没有表达**

- **JSON／MD 的分界、产物字段、内容格式** —— 一个字都没有；**发布／签名／密钥／tag** 也没有。
- **Android 端怎么做**（Compose 的文本布局 API、两端规则怎么共用）——只写在 §6 的代价里。
- **题名／身份行／笔记区的折行**（只做了正文的折行规则）；**异文／来源**的排版。
- **`text-align: justify`（两端对齐）**、半角／全角混排的完整规则、`word-break` 与西文混排的细粒度交互。
- **连续标点**（如 `甲，。乙` 这种相邻两个句读）在**极窄容器**下**两条禁则冲突**的情形（逗号不能起行、句号也不能起行，前一字下移之后行首仍是标点）—— **本页没有夹具覆盖这一格**，如实记为**未覆盖／需拍板**；本页所有夹具都不会触发它。
- **多行（≥4 行）时的版面表现**：R3B 窄容器给到 4 行、逐行都量了，但没有为「很多行」另做版面设计。

**本页没验**

- 只在**本机无头 Chromium**（`file://`、DPR 2、本机字体回退）下跑过；**没有**真机／Android／iOS Safari。
- **字体回退会改断点**：本机解析到的是 `Microsoft YaHei UI`；换成别的字体，`17.765` 这个推进宽与上面**所有**断点都要重算（自检会把推进宽**独立实测**一遍并比对，不一致就报错）。
