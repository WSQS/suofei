# 源文件格式候选原型（H 组：内容数据的组织方式）

> **2026-10-15 由子会话（`wt/child-ed466654`）产出**，用途：让用户**看见**「源 MD 怎么写、内容放哪、编译后字段是什么」，而不是继续抽象地选「文本 vs 结构化」。
>
> **性质：讨论原型。不是生产实施、不是数据迁移、不是发布，也不是已采纳规格。** 样例产物 JSON 一律是**样例**、**不是正式 `dist/content.json`**；本目录**未动** `content/**`、`tools/**`、`schema/**`、真产物或任何冻结指纹。
>
> **来源 commit**：`4506e59`（`git rev-parse --short HEAD`；即本目录创建时的工作树 HEAD）。

## 这份原型回答的三个问题

| 文件 | 它回答什么问题 | 产物侧 |
|---|---|---|
| [`a-detail-in-body-text-field.md`](a-detail-in-body-text-field.md) | 详情**整块**进正文，产物只带**一坨文本字段** `detail`，源与产物长什么样、代价是什么 | `detail`（string） |
| [`b-frontmatter-structured-minimal-change.md`](b-frontmatter-structured-minimal-change.md) | **不重构源文件**（`variants` 留在 front matter），只加一个结构化字段，代价是什么 | `+segmentation` |
| [`c-collection-lift-detail-in-body-structured.md`](c-collection-lift-detail-in-body-structured.md) | **集合级元数据上提** ＋ 详情进正文，但产物**仍结构化**，源文件怎么组织、注入/覆盖规则是什么 | `variants` ＋ `segmentation` |

配套物：
- `samples/` —— 三个候选的《行行重行行》全样例（每候选各 3 个：无笔记 / 有笔记测试夹具 / 无详情），加上候选 C 的集合文件。**全部是样例，与 `content/` 无关。**
- `demo-parse-samples.mjs` —— **演示脚本**（注释与输出都写明「**演示用，不是编译器**」）：只读 `samples/`，把样例 MD 解析成样例 JSON，并跑「**逐诗逐行**」的正文切分自检。**绝不读 `content/`、绝不写任何东西。**
- `demo-output.txt` —— 上面脚本的实际输出（样例 JSON ＋ 自检表）。

运行：`node items/content-format/prototypes/demo-parse-samples.mjs`

## 三个候选在两条轴上的位置

```
                        轴②源侧：正文区段 | front matter 结构字段
轴① 单文件自足          A(正文, 文本字段)   B(front matter, 结构化)
     集合级上提         C(正文, 结构化)     —— 本批未出 ----
                        产物：文本  |  结构化
```

- **A**：单文件自足 ＋ 正文区段 ＋ 产物**文本字段**。
- **B**：单文件自足 ＋ **front matter 结构字段** ＋ 产物**结构化**（＝「零源重构」对照）。
- **C**：**集合级上提** ＋ 正文区段 ＋ 产物**结构化**。

三个候选落在两条轴的**不同角**；本批**刻意没有做满交叉积**（例如「上提 ＋ front matter ＋ 文本字段」未出）。

**⚠️ 本批三候选中没有任何一对是干净的单变量对照**（相邻对**至少两处不同**）——这是「**刻意不做满交叉积**」的直接后果：

| 一对 | 这两处不同 |
|---|---|
| A ↔ B | ① 产物携带（文本 vs 结构化）　② 源侧承载（正文区段 vs front matter） |
| A ↔ C | ① 产物携带（文本 vs 结构化）　② 轴①（单文件自足 vs 集合级上提） |
| B ↔ C | ① 轴①（单文件自足 vs 集合级上提）　② **源侧承载（front matter vs 正文区段）** |

⇒ 讨论时请把每个候选当**一个整体形状**读，**不要当消融实验（ablation）读**：它们不是「只差一个开关」的对照——**任何一对相邻候选都同时动了两件事**，所以不能从某一对里读出「单独这一个变化值多少钱」。

- 若将来**确实**需要一个干净对照（例如「上提 × front matter × 文本字段」这一格），**可以再补一个隔离候选**——这是**可选项**，**本批不做**。

## 继承了什么（＝用户已表达的方向）

1. **详情＝md 正文的一部分**（用户 2026-10-15：「详情可以是 md 正文当中的一部分」）——A 与 C 都据此把详情节放进正文。
2. **`variants` 长块不要留在 front matter**、相关内容移入正文的「详情」部分——A 与 C 据此把异文写进正文；**B 明确标注相抵**（它把 `variants` 留在 front matter，作为「不重构」对照）。
3. **同书不同本／分段依据进详情**（用户：「进，但是只是放在一个详情页的字段当中」）——三个候选都给「分段依据」留了位置（A 在 `detail` 里、B/C 在 `segmentation`）。
4. **保持「诗歌原文 / 个人笔记 / 详情」三者分离**——A/C 把三者分成 `stanzas`（原文）／`## 笔记`／`## 详情`，产物仍是三个字段。

## 没表达什么（＝本原型**没有**声称已被采纳的那一层）

- 「集合级默认值上提」——**用户未答**（`items/content-format/item.md` 开放区域第 2 条），本原型只在候选 C 里展示形状，**不是结论**。
- 「`## 详情` 作切分点」「`### 异文`／`### 分段依据` 子节名」「用 `detail`／`segmentation` 这些字段名」「`id` 从文件名得」——**全部是此前助手草案或本原型的草案名**，未整套采纳；文档内凡新字段名一律标「草案」。
- 「详情在产物里用文本字段还是结构化字段」——**仍在问用户的 `q-06b547dc`**，本原型给的是三条可比较的形状，**不是替用户选**。

## 四条必须写准的口径（用户 2026-10-15 的纠正）

1. **源格式变化本身不自动要求升 `formatVersion`**。只有**确实改了「正式产物字段集」**才按 **B 规则（字段集一变就升）** 升。⇒ 每个候选文档都**明确写出**「它有没有改产物字段集」，改了就是一次**不可逆**动作，明确标出。
   - 直接后果：**「把 `variants` 挪进正文」不升版**；**「上提集合级字段」不升版**；**只有产物换了键才升**。
2. **不要继承「说重了」的那句**。准确口径是：**旧 APK 拒收更高 `formatVersion` 的内容**（退回内置内容、不解析）；但**装新的同签名 APK 是普通覆盖安装，不需要卸载重装**。「丢密钥才要卸载重装」是**另一回事**（那是签名不同，与格式版本无关）。
3. **切分验证按「逐诗逐行比较」**，不能只靠「19 首印刷行合计 127」或「禁止 `#`」当唯一证明；**不用**「详情里的字句不出现在正文里」这类**子串断言**（来源文本与正文出现相同字句是合法的，会误伤）。⇒ 用「切出的正文行 == 详情切分点之前的非空行，**逐行相等**」，并**分开报每首诗的行数**。
4. **不宣称免费**。源文件重构**仍有编辑／编译／校验成本**，逐候选在各自 §5 写清；没有任何一个候选是「零成本」。

## 「有没有改产物字段集」一览（三个候选的明确结论）

| 候选 | 字段增删 | 改了产物字段集？ | 是否升 `formatVersion` |
|---|---|---|---|
| **A** | ＋`detail`；−`variants`（含 `variants[]`／`.text`／`.note`） | **改了** | **是，升到 2（不可逆）** |
| **B** | ＋`segmentation` | **改了** | **是，升到 2（不可逆）**（若不加该字段则零变更，但分段依据显示不了） |
| **C** | ＋`segmentation`；`variants` 键保留（值来源改自正文） | **改了**（仅因 `segmentation`） | **是，升到 2（不可逆）**；**其中「集合级上提」这一半单独做时零变更** |

> 三条都给出「如果把 `segmentation` 去掉会怎样」：A 仍因 `detail`／`variants` 变而升；B 与 C 的**上提／承载**部分则零变更。**升版是可逆性最贵的一步**，值得单独决定。

> **防误读（客户端代价）**：候选 C「客户端不必动异文渲染」这句**只指保留了 `variants` 结构化**；**新增 `segmentation` 的解析与展示仍需做（两端各一处）**。**任何新增字段的解析与显示都是活**——不要把 C 简化成「客户端几乎不动」。

## 诚实边界

- 本目录**只新增文件**，**未修改**任何既有文件或真数据；`demo-parse-samples.mjs` **只读** `samples/`。
- 演示脚本**不是编译器**，解析规则是刻意写小的一段；正式解析/校验/错误码仍以 `tools/` 与 `docs/design/content-contract.md` 为准（本原型**未改** `tools/`）。
- 候选里的《行行重行行》数据（8 行正文、3 条异文）抄自 `content/poems/gushi-shijiu-shou-01.md`（未改一字）；「分段依据」那句话是**集合级事实**（底本通篇连排、篇内无空行）的复用，**不是**本原型新校的结论。
- 笔记样例**明确是测试夹具**（正文里就写着「这是测试夹具笔记，不是用户笔记」）；本原型**不代用户写任何第一人称笔记**。
- 三个候选的字段名、子节名、切分规则都是**草案**；它们**不构成**对 `docs/design/content-contract.md` 的修订。
