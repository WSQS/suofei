# 顶层 `dynasties` 怎么处置 ＋ 朝代组序注册表的内部结构（**并列方案，不自行定**）

> **性质：待审材料，不是实施授权，也不是已采纳规格。**
> ⚠️ 这两件事**用户没有逐字段确认** ⇒ 本文**只出方案**：每案写清形状、代价、以及它拖累哪些既有代码。**不排推荐、不写「推荐」、不选。**
> 方案示意都是**文件**：`top-level-candidates/*.json`（每个文件都带 `_note` 写着「**方案示意，不是产物、不是 schema、不参与发布**」）。

---

## 0. 为什么删了 `dynastyOrder` 之后这件事必须回答

- 「目录只显示**有内容的**组、按**时代**排序」是已确认范围（`CONTEXT.md`）。
- v1 把这个顺序放在**两处**：每首诗的 `dynastyOrder`（作者写，冗余快照）＋ 顶层的 `dynasties` 声明表（权威）。
- 本稿每首只剩**一个**中文 `dynasty` ⇒ 组序必须由**别处**提供。可去的地方只有三类：① 顶层一张表；② `poems` 数组次序（编译期算好）；③ **重新放回每首诗**（一个编译期算好的整数）。
- 另有一个**原先没被问过**的问题一起摆出来：**注册表里还需要 `key` 吗？**
  v1 的 `key`（`han` 这种稳定 ASCII 标识）是**诗对象分组的身份**（`poem.dynastyKey`）；本稿诗对象里**没有 key** ⇒ 若顶层也不放，`key` 就**无处可引用**，它的存在意义需要重新说明。

**注册表现在的内部结构（只读核对，本材料不改它）**：`tools/lib/dynasties.mjs` 是一张**手写表**，`{ key, label, order }` 各 11 条 —— `先秦 0`／`han 汉 100`／`魏晋 200`／`南北朝 300`／`唐 400`／`宋 500`／`元 600`／`明 700`／`清 800`／`近现代 900`／`未详 9999`；查表规则是**精确匹配 label、不做别名猜测**（未声明 ⇒ 编译失败 `DYNASTY_UNDECLARED`）。**当前内容只用到 `汉` 一条**（19/19 首）。

## 1. 案 ① —— 产物里保留一份顶层注册表（`key` → `label` → `order`）

示意：`top-level-candidates/option-1-registry.json`

```json
"dynasties": [ { "key": "han", "label": "汉", "order": 100 } ]
```

- **形状**：与 v1 顶层同形（v1 也只列有内容的组）。诗对象里只有 `dynasty`（`"汉"`）。
- **好处**：组名、组序、稳定标识**都还在一处**；`dynasty` 的值可与 `dynasties[].label` 交叉校验（编译器保证一致）；将来若要 i18n 或改显示名，有 `key` 可依；「已知朝代集合」有出处（客户端能像 v1 那样报「未声明的朝代」）。
- **代价**：
  1. `label` 与诗的 `dynasty` **同一信息出现两次**（v1 就有这个问题，靠编译器保证一致）；
  2. **`key` 在诗对象里已无引用** ⇒ 它变成「只有客户端/审计在读」的字段；得**显式说明用途**，否则是死字段（或干脆去掉，见 ①c）；
  3. 顶层键保留 ⇒ 两端仍要改代码（现在按 `poem.dynastyKey` join 顶层表，得改成用 `poem.dynasty` 匹配 `dynasties[].label`）。
- **子案**：
  - **①b** `"dynasties": ["汉", …]` —— 只列有序 label，**不带任何字段**。更小；但**组序变成数组下标**（顺序即语义，客户端不得重排），且没有 `key`。
  - **①c** `"dynasties": [{ "label": "汉", "order": 100 }]` —— 保留显式 `order`（不靠下标），去掉 `key`。代价是**丢了稳定标识**（改显示名就是改身份，见 `source-vs-derived.md` §2.2）。

## 2. 案 ② —— 产物里**不留**注册表，组序由编译期算好

### ②a 组序 ＝ `poems` 数组里的**首次出现顺序**

示意：`top-level-candidates/option-2a-order-in-array.json`（顶层只有版本键 ＋ `poems`）

- **形状**：客户端**按 `poems` 次序首次见到某个 `dynasty` 时就建组**，照数组走，不重排。
- **好处**：产物最小；与**已经定了的**口径「编译期是唯一排序权威、客户端不得重排」（契约 §2.1.1）天然一致 —— 客户端只是按数组渲染。
- **代价**：
  1. 「组序」变成**数组性质**，客户端**无法独立得知**（做「跳到某朝代」「只看某组」时没有依据，只能扫数组）；
  2. 客户端若自作主张按 `dynasty` 排序（拼音/码位）就会**和编译期打架**，而这种错**不显形**（v1 有 `order` 可比对，现在没有）；
  3. **「已知朝代集合」失去出处**：v1 能报「`dynastyKey` 未在 `dynasties` 中声明」（`web/app/content.js`、`ContentParser.kt` 都这么做），现在客户端只能各自硬编码一张表，或干脆不校验。

### ②b 不留注册表，改为**每首诗带一个编译期算好的组序整数**

示意：`top-level-candidates/option-2b-per-poem-group-order.json`（名字沿用 `dynastyOrder`）

- **形状**：诗对象多一个整数键（如 `dynastyOrder: 100`），值由编译期查表得来，**作者不写**。
- **好处**：客户端能**独立得知**组序、能做「跳组/筛组」；分组逻辑不需要顶层表。
- **代价**：
  1. **与用户 2026-10-15 的「每首只保留一个 `dynasty` 字段」相抵** —— 每首又变成**两个**与朝代有关的键（本材料**不判断**这条相抵能否接受，需要用户明确）；
  2. 同一组里**每首都重复同一个整数** —— v1 的冗余快照问题**原样回来**（组序改一次，全部内容重编译）；
  3. 若这个键还叫 `dynastyOrder`，名字与 v1 撞上，读者容易以为「没删」。

## 3. 案 ③ —— 别的：编译期直接输出「已分组的两层结构」

示意：`top-level-candidates/option-3-grouped-poems.json`

```json
"groups": [ { "dynasty": "汉", "poems": [ … ] } ]
```

- **形状**：顶层从 `poems` 换成 `groups`；**组序＝`groups` 数组次序**；组内诗的 `dynasty` **仍是**那一个中文值（不另带组序键）。
- **好处**：① 客户端**不需要**自己分组（组与组序都是数组性质），目录页可照两层数组直接渲染；② 诗对象保持「一个 `dynasty`」，不违反用户的选择；③ 组名就在 `groups[].dynasty` 上，不用另找。
- **代价**：
  1. 顶层**换形**（`poems` ⇒ `groups`）⇒ 两端解析、以及所有现存断言/夹具都要改（比 ①② 改得多）；
  2. `groups[].dynasty` 与每首诗的 `dynasty` **冗余**（同组 N 份；组名改字要全组一致）；
  3. 「已知朝代集合」**仍无独立出处**（同 ②a 的第 3 条）；
  4. 若将来要一份「全部诗」的扁平视图，客户端得自己拍平。

**③ 的同类做法（不另给示意文件）**：把组序表放到**两端的运行时配置**里（例如 Web 的 `about-fields.json` 那种运行时副本）。代价是**两端各存一份顺序表**，而契约已明确「以声明表为准，不要各处拼」⇒ 这会把当初修掉的**权威分裂**风险重新引入。

## 4. 四案对照（只列事实，不排序、不打分）

| | 顶层有注册表 | 组序在哪 | 诗对象里有几个朝代相关键 | 「已知朝代集合」有出处 | 顶层形状是否要换 |
|---|---|---|---|---|---|
| ①（含 ①b/①c） | 有 | 表里的 `order`（①b 是下标） | 1 | 有 | 不换（与 v1 同形） |
| ②a | 无 | `poems` 数组次序 | 1 | **无** | 不换（少一个键） |
| ②b | 无 | 每首诗的整数 | **2** | **无** | 不换（每个诗对象多一键） |
| ③ | 无 | `groups` 数组次序 | 1 | **无** | **换**（`poems` ⇒ `groups`） |

**与 `key` 有关的、四案都没自动解决的一件事**：`key` 的去留（① 保留／①c 去掉／② 不在产物／③ 只在 `groups` 里）与「`dynasty` 是否允许未声明的值」是**两件事**，需要一起想：只要 `key` 不在产物里，客户端就没有稳定标识可依。

## 6. 本材料**没有**做什么

- **没有选定任何一案**，也没有把 `key` 去留、或「组序进不进产物」定下来。
- **没有**把组序写进任何「产物」：`top-level-candidates/*.json` 全是**示意**，带 `_note`，不是产物、不是 schema。
- **没有**改 `tools/lib/dynasties.mjs`、`tools/lib/interface.mjs`、`schema/`、契约或两端代码。
- **没有**把「顶层 `dynasties` 是否保留」当成已定的问题（它是**未审**项；上一稿归档记录也把它列为「没被解决」）。
