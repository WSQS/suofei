## 1. 建议的 ID 规则（案 C2）＋ 表示法的选择

### 1.1 规范语句（**建议**）

> **ID ＝ 该源文件相对 `content/poems/` 的相对路径，去掉 `.md`，对名字做 Unicode NFC 归一化，并把目录分隔符 `/` 统一写成 `-`；最后对结果做全库唯一性校验（NFC ＋ 小写折叠后比较），冲突 ⇒ 报错。**

示例（两层中文目录）：`content/poems/汉/古诗十九首/行行重行行.md` ⇒ ID `汉-古诗十九首-行行重行行`。

### 1.2 分隔符：保留 `/` 还是换成 `-`（**必须二选一**）

> **〔2026-10-16 已定：取案 C2〕** 下面并列只作留痕（C1 未被采纳）。

| | **案 C1：保留 `/`** | **案 C2：换成 `-`（建议）** |
|---|---|---|
| ID 例 | `汉/古诗十九首/行行重行行` | `汉-古诗十九首-行行重行行` |
| 可逆性 | **可逆**（能反解出层级） | 不可逆（分不出哪一截是目录） |
| 现有 Web 路由 | ✅ **两种都能用**：正规生成的链接是 `encodeURIComponent(id)`，其中的 `/` 被编成 `%2F` ⇒ 现有 `poemPattern = /^\/p\/([^/]+)$/` **能匹配**，随后 `decodeURIComponent` 解回路径；`#/p/<id>/detail` 同理（详见 §4.1）。**C1 不需要改路由。** | ✅ **同样能用**：ID 里没有 `/`，中文照样被 `encodeURIComponent` 编码 |
| 唯一的差别：**手写链接** | ⚠ **用户手写、未编码 `/` 的链接**匹配不上任何路由 ⇒ `parseHashString` 返回 `index` ⇒ **静默落到目录**（`web/app/main.js` 的兜底；已用现有代码验证，见 `demo-id-v2.mjs` ⑤）。这是**手写链接**的问题，**不是正规生成链接不可用** | 手写链接里没有 `/` ⇒ 不存在这条歧义（中文未编码时依赖浏览器自动编码，见 §4.1 的「未实测」） |
| 代价 | 仅这一条**手写链接**的坑（正规生成/分享的链接不受影响） | 丢层级（不可逆）；**可能撞上文件名里本来就有的 `-`** ⇒ 换完之后**必须再查一次唯一性**（具体冲突例见 §1.3） |

**建议：案 C2（`/` → `-`）。理由**：① 它让 ID 成为一个**单 token**，可以放心用在 URL、日志、比较、以及任何「手工拼链接」的地方（C1 的唯一限制正好落在**手写链接**上）；② **两种写法的路由都能用**，所以这条选择**不取决于路由**，只取决于「ID 要不要是一个单 token」与「要不要保留层级可逆性」。
**代价（如实说）**：丢层级可逆性；并且**换分隔符本身会引入新的撞名**（见 §1.3），所以唯一性校验必须在**替换之后**做。

> 另有一个不推荐也不禁止的第三写法：用一个不易自然出现的分隔符（如 `__`）代替 `/`，既不含 `/` 又**保留可逆性**。代价是多一个「不要用 `__` 命名」的隐式约定。

### 1.3 「换成 `-`」的代价，用**具体例子**说

夹具 `name-tree-fixture-v2/dash-collision/`（真实文件，已提交）：

```text
汉/古诗十九首/行行重行行.md        ⇒ 案 C2 ID = 汉-古诗十九首-行行重行行
汉-古诗十九首-行行重行行.md        ⇒ 案 C2 ID = 汉-古诗十九首-行行重行行   ← 与上一行**同 ID**
```

⇒ 案 C2 **冲突 1 组**（必须报错）；案 C1（保留 `/`）**冲突 0 组**。这是选 `-` 必须一起接受的代价；`demo-id-v2.mjs` 里对这条**会响**（`--scan` 该目录 ⇒ **EXIT≠0**）。

## 3. 「只用紧邻父目录名 + basename」（案 D2）什么时候**仍然冲突**

| 情形 | 相对路径 | 案 D2（仅父目录 + basename） | 案 C2（全根相对路径） | 案 C1 |
|---|---|---|---|---|
| **两棵不同子树下有同名父目录**（已用真实夹具验证） | `甲/汉/行行重行行.md` 与 `乙/汉/行行重行行.md` | **`汉-行行重行行`（两处相同 ⇒ 冲突）** | `甲-汉-行行重行行` ／ `乙-汉-行行重行行` | `甲/汉/…` ／ `乙/汉/…` |
| 靠更上一层才能区分 | `古诗十九首/汉/行行重行行.md` 与 `其他/汉/行行重行行.md` | 同上冲突（都是 `汉-行行重行行`） | 不同 | 不同 |
| 同名的**诗名**出现在不同集合 | `古诗十九首/无题.md` 与 `唐诗/无题.md` | 父目录不同 ⇒ **不冲突**（这条 D2 能过） | 不同 | 不同 |
| 文件从根挪进目录 | `行行重行行.md` → `汉/行行重行行.md` | `行行重行行` → `汉-行行重行行`（**ID 变**） | `行行重行行` → `汉-行行重行行`（**也变**） | 变 |

**结论**：案 D2 只在「**整库最多一层目录、且所有父目录名互不相同**」时够用。一旦层级加深、或不同子树出现同名目录，它就会撞 —— 这正是「避免仅父目录仍冲突」要解决的问题，**也正是全根相对路径（C1/C2）存在的理由**。

## 4. 只读核到的现状（中文编码／路由解析／客户端）——**没有改任何代码**

### 4.1 Web 路由（`web/app/config.js`、`web/app/main.js`）

| 事实 | 原文/证据 |
|---|---|
| 三条路由 | `index: '#/'`；`poem: (id) => '#/p/' + encodeURIComponent(id)`；`detail: (id) => '#/p/' + encodeURIComponent(id) + '/detail'`；`about: '#/about'` |
| 诗页模式**排除 `/`** | `poemPattern: /^\/p\/([^/]+)$/`，注释原文：「**id 里不含 `/`（否则会与详情页的 `/detail` 后缀相撞）** —— 所以模式里排除 `/`」 |
| 详情模式先匹配 | `detailPattern: /^\/p\/([^/]+)\/detail$/`（`parseHashString` 里先试它，否则详情会被当成 id 为 `<id>/detail`） |
| **中文一定被编码** | `ROUTES.poem(id)` 用 `encodeURIComponent`；`demo-id-v2.mjs` 打印的真实值形如 `#/p/%E6%B1%89-...`（中文 ⇒ `%E6%B1%89`…） |
| **`/` 被编码成 `%2F`** | 仓库已有断言：`web/tests/e2e-cdp.mjs` `eq('诗页路由', ROUTES.poem('abc/def'), '#/p/abc%2Fdef')` |
| **匹配不上 ⇒ 落到目录** | `parseHashString` 末尾 `return { kind: 'index', id: null }`（`main.js`）⇒ 路由解析不出任何页面时**显示目录**，不是 404、也不是「找不到这首诗」 |
| id 进地址栏的是**契约 id**，不是标题 | e2e 断言 `location.hash` ＝ `#/p/<id>`，且不含 `encodeURIComponent(title)` |
| 找不到 id 时 | `render.js` `getPoem()` 返回 `null` ⇒ 渲染 `view--missing`，文案 **「找不到这首诗：`<id>`」**（**不回退目录**） |

**由此得到的两个可判断结论（代码级，不依赖浏览器）**：

- 由程序生成的链接（`ROUTES.poem`）**中文/斜杠都会被编码**，所以 C1、C2 都能往返解码（`demo-id-v2.mjs` ⑤ 已断言 `kind=poem, id=…` 与 `kind=detail, id=…`）。
- **手写的、含字面 `/` 的链接**（案 C1 的形态）**匹配不上任何路由 ⇒ 静默落到目录**（已断言 `kind=index`）。这是**手写链接**的限制，**不是** C1 的正规生成链接不可用（上一行已说明两种都能往返）。
- **手写的、中文未编码但无 `/` 的链接**（案 C2 的形态）：能否命中取决于**浏览器是否把地址栏里的非 ASCII 自动 percent-encode**。**这属浏览器行为，本材料未实测**（材料里只声称：生成端一定编码）。

### 4.2 契约与校验（现状）

| 事实 | 证据 |
|---|---|
| ID 的值模式是**全小写 ASCII ＋ 以 `-数字` 结尾** | `tools/lib/interface.mjs`：`ID_REGEX = /^[a-z0-9]+(?:-[a-z0-9]+)*-\d+$/`；`schema/content.schema.json`：`"pattern": "^[a-z0-9]+(?:-[a-z0-9]+)*-\\d+$"` |
| 现编译器还要求 front matter `id` 等于 basename | `tools/lib/content-build.mjs`（`ID_FILENAME_MISMATCH`）— 规则 ② 之后这条口径要重述 |

⇒ **中文 ID 违反现模式**（中文不在 `[a-z0-9]`，且新 basename 不以 `-数字` 结尾）⇒ 采纳中文 ID **必须改**契约散文、`ID_REGEX`／`ID_PATTERN` 与 schema 的 `pattern`。
⚠ 这**不是「字段集」变化**（键没变，只是值形态变了）；但它**仍是**一处契约/校验改动，如实记在这里。

### 4.3 Android（只读核）

- `android/app/src/main/AndroidManifest.xml` **只有 `MAIN`/`LAUNCHER` 的 intent-filter**，**没有** `<data android:scheme=...>`／deep-link／`assetlinks` 入口 ⇒ **Android 端根本打不开 `#/p/<id>` 这类链接**。
- app 代码里**没有**哈希路由解析（`grep '#/p'`／`Uri` 在 `ui/` 下无命中）。
- ⇒ **改 ID 对 Android 深链接零影响**；Android 只是拿内置产物里的 `id` 当查表键（首页→诗页→详情页都在应用内跳转）。

### 4.4 一个必须一起看的事实：**站点已经上线**

`docs/status.md`：**`v0.1.1` 已发布**，Web 站点 `https://wsqs.github.io/suofei/` 在线，**哈希路由（`#/、#/p/<id>、#/p/<id>/detail`）已在线上**；同一处还写着一条**已定决策**：「保持哈希路由……**不动发布白名单与旧链接**」。
⇒ 「改用中文 ID」**会与那条已定决策相抵**（旧链接会失效），这不是理论代价，而是**线上已经存在的可分享链接**。

## 5. 旧 ASCII ID 的迁移（⚠ 本节是重点）

**先说结论**：**19 首旧 ID 会全部改变**，`id-migration.md §4` 那条「案 A 零迁移、19 个旧 ID 保持不变」**不再适用**。

| # | 旧 ID（现状，线上） | 新 ID（案 C2，两层目录） |
|---|---|---|
| 01 | `gushi-shijiu-shou-01` | `汉-古诗十九首-行行重行行` |
| 02 | `gushi-shijiu-shou-02` | `汉-古诗十九首-青青河畔草` |
| 06 | `gushi-shijiu-shou-06` | `汉-古诗十九首-涉江采芙蓉` |
| … | …（19 首**全部**如此） | … |

### 5.1 迁移方案（并列 ＋ 代价）

> **〔③ ④ 已被用户 2026-10-16 否决〕** 用户已定「**直接换、不做兼容**」⇒ 下表 ③（双 ID 期）与 ④（Web 构建期静态映射）**不采纳**，留痕备查；收口稿见 `id-final.md` §6。

| | **① 保留旧 ID ＋ 旧→新别名表** | **② 直接换新 ID（旧链接断）** | **③ 双 ID 期（保留一段时间再切）** | **④ Web 构建期静态映射（不改诗字段）** |
|---|---|---|---|---|
| 做法 | 产物/客户端里存一张旧 id → 新 id 的映射，旧链接重定向到新 ID | 产物只带新 ID | 产物**同时**带 `id`（新）与 `legacyId`（旧），客户端两者都能解析；过一段时间删 `legacyId` | **Web 构建期**产出一份静态「旧 id → 新 id」映射（**一份、版本控制**，或**由构建生成**以防手工漂移）；路由兜底时先查它再渲染。**产物 JSON 不动**（不加诗字段） |
| 旧 `#/p/<旧id>` | **继续可用** | **断**：Web 显示「找不到这首诗：`gushi-shijiu-shou-01`」（已验证，**不回退目录**）；Android 无入口、无影响 | **继续可用** | **继续可用** |
| 代价 | 要么加产物字段，要么用一张静态映射表；且从此「id ↔ 源文件一一对应」这条简洁性被打破；**没有删除时机** ⇒ 长期留一张手写映射 | 线上已发布的链接**实际失效**；没有任何机械闸会提醒（字段集门只看键、`contentVersion` 不表示 ID 变）；优点：产物干净、无遗留 | **加字段**（与「不加字段」相抵）；会触发**又一次字段集变化**（`formatVersion` 按 B 判据要升、并写入 `formatVersion` 账本）；需要一个「**何时删 `legacyId`**」的运营决定；期间客户端要接受两种 id 形态查表 | **谁维护**：**只有一处**（Web 侧那份映射）—— **Android 没有 URL/deep-link 入口 ⇒ 不必再养一份**（也不会两端漂）。**漂移风险**：手工维护就会与源文件名脱钩 ⇒ 建议**由构建生成**；而「生成」需要一个旧 id 的来源（如一次性的迁移清单，或从**上一个已发布产物** `content.json` 抽）。**何时失效**：只在**这份映射还在构建里**时有效 ⇒ 删除时机要显式决定（不删则长期留一张表） |
| 与规则②的关系 | 不违反「源里不手填 id」，但**引入了产物级别名**（用户没批准过） | 最贴合「ID 由相对路径生成」 | 是 ① 的一种（带删除期的 ①） | 不改源、**不加诗字段**；是**兼容资产**（**是否加，同样要用户拍板**） |

### 5.2 建议（并**明确哪些要用户拍板**）

- **若「旧链接不必保」** ⇒ 选 **②**：只改 ID，产物最干净、无字段、无遗留。（代价：线上旧链接失效，需在发布说明里写清。）
- **若「旧链接要保」** ⇒ **③ 与 ④ 并列**（两条都写清了成本），取一由用户定：
  - **③ 双 ID 期（加 `legacyId`）**：改**产物字段** ⇒ 触发又一次字段集变化（按 B 判据升 `formatVersion`），需要「何时删 `legacyId`」的运营决定。
  - **④ Web 构建期静态映射（不改诗字段）**：只加一份**兼容资产**（映射表 ＋ 路由兜底）；维护点只有一处（Android 无 URL 入口，不必再养一份），代价是这份映射的**漂移风险**与**删除时机**。
- ⚠ **一条口径要分清**：本轮**不批准的是「改产物字段」**（所以 ③ 需要单独授权）；**「加一份兼容资产（静态映射表 ＋ 路由兜底）」是另一件事**，**同样要用户拍板** —— **不要**把「不加字段」**扩大**成「禁止一切兼容资产」。
- **不推荐 ①**：它迟早要维护一张没有删除时机的映射，而 ③（或 ④）就是它加一个删除期／换一种承载的版本。

## 6. 安全边界（保留七条 ＋ **新增两条**）

### 6.1 保留的七条（与 `rules-v3.md §7.4` 同一建议）

| 边界 | 建议 |
|---|---|
| 扫描根 | **只扫 `content/poems/` 之下（含递归子目录），不越出该根** |
| README 与说明文件 | **`_` 前缀（文件或目录）＋ `README.md` ⇒ 忽略并计数** |
| 符号链接 | **不跟随；遇到即报错**（非零退出） |
| 隐藏文件与临时文件 | **`.` 开头、`~$`/`~` 结尾 ⇒ 忽略并计数** |
| Unicode 形与大小写 | **NFC ＋ 小写折叠后比较 ⇒ 不同形当重复，报错**（细化见下 6.2① ②） |
| 空目录 | **忽略并计数** |
| 非 `.md` 文件 | **poems 根之内、不在排除清单里的非 `.md` ⇒ 报错** |

### 6.2 新增两条

**① 中文文件名的 Unicode 归一化（NFC／NFD 会被当不同文件名）**

> **建议**：**在扫描的第一步**（刚拿到条目名时）就对名字做 **NFC 归一化**；**判重**与**ID 派生**一律用**归一化后的名字**；并且**若磁盘上的名字本身不是 NFC，就报错并提示先在磁盘上归一化**（新增告警码 `non-nfc-name`）。

- **理由**：NFC 与 NFD 会**看起来一样、字节不同**（已实测真值：`U+8C48`（豈）与 `U+F900` 在 NFC 下**同形**）；macOS 的文件系统习惯存 NFD ⇒ 同一首诗在 mac 与 Windows 上可能生成**不同 ID**，链接/产物会随机器漂。
- **放在哪一步**：**第一步**（早于排除规则与判重），这样「磁盘名检查、判重、ID、路由编码」用的是同一个形态；产物 ID 建议用 **NFC**。
- **若你不同意**：不做归一化 ⇒ 同一库在不同平台可能编出不同 ID；只归一化但**不报错** ⇒ 一个 NFD 名字会静默产生一个「看起来重名」的 ID。

**② Windows／macOS 路径大小写差异（同一文件两种写法）**

> **建议**：**在判重那一步**（与 ① 同一处）按 **NFC ＋ 大小写折叠**比较**相对路径**；只有大小写不同的两个名字 ⇒ **当重复并报错**。

- **理由**：Windows/macOS 的文件系统**大小写不敏感**（同一文件两种写法在本地可能只存在一个），而 Linux/CI **敏感**（仓库里可以同时存在两个）⇒ 只在部分平台重复的路径会让**产物随平台而变**。
- **若你不同意**：按字节比较 ⇒ 同一个库在不同平台上可能编出不同 ID，且**在本地看不见**。

### 6.3 这两条不改已定 4 条规则

① ② 只影响「什么样的源算合法」「ID 用哪个形态」；不改变产物的**键**与**键序**，也不改变规则 ①③④。

## 7. **不加字段**（明说）

- **根路径与目录层级用户没有逐项定** ⇒ 本文只给**候选与建议**（§1、§2），不当作已定。
- **不引入 `id:` 之类的源字段**（与规则 ② 相抵）。
- **不引入「路径覆盖字段」**（如 `path:`／`routeId:`）—— 那会与「不再手填 id」相抵，并把重复 ID / 不一致问题请回来。
- **需要用户单独批准的两件事**（为保旧链接）：**③ 加 `legacyId` 产物字段**、或 **④ 加一份 Web 构建期静态映射（兼容资产，不改诗字段）**。口径要分清：「**不加字段**」约束的是**产物字段**，**不等于**禁止一份独立的兼容资产；两件都不批准 ⇒ 实际只剩 §5 的 ②。

## 9. 本材料**没做、没验**的

- **没做**：搬任何源文件、改 `tools/`·`schema/`·`web/`·`android/`·`content/`、改 `ID_REGEX`/schema、发布、push、打 tag。
- **没验**（浏览器行为）：地址栏里**未编码中文**（案 C2 手写链接）是否被浏览器自动 percent-encode、`location.hash` 读回形态。**代码级已验证**的只是「生成端一定编码」「含字面 `/` 的手写链接 ⇒ 静默落目录」。
- **没定**（等用户拍板）：**目录层级与根路径**、**ID 写法**（C1/C2/D2）、**分隔符**、**旧 ID 迁移选 ② 还是 ③**（以及是否批准加 `legacyId`/别名表）、§6.2 两条边界的处置。
- **没验**：真机/模拟器；两端实现改动（只是**只读核到的现状＋代价陈述**，不是已完成的活）。
