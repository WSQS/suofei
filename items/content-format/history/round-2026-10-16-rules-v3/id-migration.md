# 文件名 ID 迁移核查（**我独立核的，不是转述**）

> **〔已被 2026-10-16 的决定取代〕见 `id-and-naming-v2.md`。** 用户 2026-10-16 明确中文目录/文件名 ＋「ID 带上文件夹名字」⇒ ID 不再等于 basename ⇒ 本文 §4 那条「**案 A 零迁移、19 个旧 ID 保持不变**」的建议**不再适用**（旧 ASCII ID **19 首全部会变**，迁移方案并列见 v2 稿）。本文 §1–§3 的**核查事实与断链后果仍然有效**，原样保留。（最终收口：**取案 C2、不做兼容** ⇒ 旧 ID **19 首全部失效**、无 alias、无重定向，见 `id-final.md`。）

> **性质：材料，不是实施。** 本文回答：新规则 ②（**ID 由文件名生成**）下，**19 首「按文件名生成的 ID」与「现在手填/产物里的 ID」是否逐字相同**；**若不同**，哪些深链接会变、后果是什么。
> **两种核对结果都写**（实际结果 ＋ 假如不同的反事实），并给出**建议**。

---

## 1. 我核了什么（一手来源）

| 来源 | 怎么核 |
|---|---|
| `content/poems/*.md` 的**文件名** | `readdirSync` 后取 19 个 `.md`，basename 去 `.md` |
| 同文件的 **`id:` 行**（front matter 手填值） | 逐文件正则取 `^id:` |
| **产物里的 `id`** | `android/app/src/main/assets/content/content.json`（**仓库里唯一的、提交在产品形状上的产物**） |
| 补充产物 | `web/fixtures/*.json`（两端用的夹具，含真实 id） |

⚠ **一处诚实说明**：任务里提到的 `dist/content.json` **在本工作树里不存在**（`dist/` 被 `.gitignore` 忽略、当前未构建）。
所以「产物 ID」我是从**已提交的** Android 内置产物 `android/app/src/main/assets/content/content.json`（`formatVersion=1`、19 首）核的 —— 这是仓库里**真实存在**的产品形状产物；Web 侧另有 `web/fixtures/*.json`。

---

## 2. 结果（**实际**）

**19/19 三者逐字相同**：

```text
文件名去 .md  ==  front matter 的 id  ==  产物 content.json 的 id     （19 首，0 处不同）
```

- 产物里 19 个 id 的**次序**也与文件名次序一致（`gushi-shijiu-shou-01 … -19`）。
- 形态也合法：`^[a-z0-9]+(?:-[a-z0-9]+)*-\d+$` 对 `gushi-shijiu-shou-01` 成立。
- Web 夹具里的真实 id 同样是 `gushi-shijiu-shou-01`／`-02`／`-06`。

⇒ **案 A（basename 去 `.md`）下，19 个 ID 全部保持，迁移代价 = 0**（源文件只是**删掉 `id:` 那一行**，产物一字不变）。

## 3. 反事实：**假如**有 ID 不同会发生什么

（本工程**没有**发生；这一段是为了「两种结果都写」并让后果可判断。）

**会变的深链接**

| 端 | 链接形状 | 位置 |
|---|---|---|
| Web | `#/p/<id>`（诗页）、`#/p/<id>/detail`（详情页） | `web/app/config.js` `ROUTES.poem(id)`／`ROUTES.detail(id)` |
| Android | **核不到**基于 id 的深链接（app 代码里没有 `#/p/` 之类的路由；只有单测 `ContentParserTest.kt` 用 id 取样） | —— |

**后果（逐条，具体）**

1. **旧链接打不开 —— 但不会落到目录**：Web 的 `getPoem(doc, id)` 找不到就返回 `null`，页面渲染成 `view--missing`，文案是 **「找不到这首诗：`<旧 id>`」**（`web/app/render.js`），**不**回退到目录索引。用户看到的是一个**缺页**，可以点「← 目录」回去，但那条被分享/收藏的链接**永久失效**。
2. **谁也不会报警**：字段集门（`tools/lib/field-set.mjs`）只看**键路径**，改名不改键；`contentVersion` 也只表示内容变了。⇒ **没有任何机械闸会拦下「ID 悄悄变了」**，只能是**用户/作者改完后发现链接失效**。这一点是「改名 = 静默的链接腐化」的根源。
3. **两端都一样**：两端都按 id 取诗，所以 Web 与 Android 会**同时**断（不是只有一端）。
4. **回滚不可能**：旧链接一旦被外部记录（书签、聊天记录、二维码），改名端无法找回旧的映射 —— 除非在应用里另放一张 **旧 id → 新 id 的重定向表**。

⇒ 结论：**「文件名 ID」把「改名」直接等价于「一次 URL 迁移」**。这正是本案要**先核（本工程恰好零风险）**再决定规则的原因。

---

## 4. 建议

1. **采纳案 A（basename 去 `.md`），不引入任何显式覆盖字段。** 理由：19/19 逐字相同 ⇒ **零迁移代价**，零断链；案 A 又与用户那句「由文件名生成 ID」**字面一致**（文件名 = basename）。由此：
   - 源里删 `id:` 是纯瘦身，产物与旧链接**全不受影响**；
   - **不需要**为「改名保值」引入什么字段。
2. **不要悄悄改成「相对路径 ID」（案 B）**：那是「由**相对路径**生成 ID」，**不是**用户选的那句；它会把 19 个 ID 全部改掉、把旧链接成批打断（详见 `rules-v3.md §7.3`）。要用案 B，必须**显式提出**并接受迁移代价。
3. **若将来确实需要「改名但链接不变」**（比如为了把某首诗归入新集合而必须改文件名），**唯一**能达到的办法是重新引入一个**手写的稳定 ID**（覆盖字段）——但**如实说**：**这与「源 MD 不再手填 `id`」正面相抵**，会把「重复 id」「手填值与文件名不一致」这类问题**请回来**，并需要新的校验。因此它是**一个新的、独立的选择**，**不应**在本轮顺手加进去。**建议**：暂不加，改名就接受链接变更（并在发布说明里写清）。
4. **顺带（不是本材料范围，只记录）**：规则 ② 之后，`tests/fixtures/fail-id-duplicate/` 这类夹具的**前提**（两个文件手填同一个 `id`）在源层面不再可能出现（id 不再手写、同名文件不可能并存）；`ID_FILENAME_MISMATCH`／`ID_DUPLICATE` 的口径需要随规则重述。**本材料不改 `tests/`**，此处只说清「要改什么」。
