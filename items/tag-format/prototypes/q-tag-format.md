| 层 | 结论 |

## 0.5 用户**已采纳**的形态（2026-10-18）——**不再重开**

```yaml
tags:
  - id: 古诗十九首
    orderInTag: 1
```

- **已采纳**：frontmatter 用 **`tags` 对象序列**；元素 **`id` 用中文**（`古诗十九首`）；**标签内次序 `orderInTag`** 写在元素里。
- **不再讨论**：ASCII slug 作 id、单独 `## 标签` 节、`- 中文名` 标量项——这三条候选已被用户这一选择取代。
- **中文 id 直接当显示名用**：⚠ **这是本草案的「最简表达提案」，未采纳**（只为少两个冗余字段而暂按）——**不是用户已决定「id＝显示名」**。显示名分离**不是本期必答**，也不再反复问。
- ⚠ **源侧「标签定义表」（人手写）与产侧「派生表/有序索引」（编译期生成）是两件事**：顶层若出现有序索引，可以按既有「**编译期是唯一排序权威**」的原则**生成**，**不等于要求用户手写标签表**；也不存在「必须手写一个空注册表」这回事（**空标签只是候选边界**）。
- **同名的不同版本**这类边界**仍未定**（本示例文件已移除那条，避免暗示已决）。

## 0.6 尚**未采纳**、仅作建议的缺省与排序（**不是用户已准的决定**）

| 情形 | 建议 | 具体例子 |
|---|---|---|
| 源里**没有** `tags` 键 | 允许省略，产物按 **`[]`** 处理（≠ `null`） | 杜甫二首若不入任何标签：`poems[].tags: []`，诗仍在 `poems`、目录照样列出 |
| ~~元素里**没有** `orderInTag`~~ | ~~允许省略，产物 `null`；排序时排在有序项之后~~ **❌ 已被 2026-10-18 用户决定替代：`orderInTag` 改为必填、不可为 null、不再“缺序后置”（见 §0.8）** | ~~同一标签下 `1`、`3`、省略、省略 ⇒ 1 → 3 → 两个 null~~ |
| **同序冲突**（两首同 `orderInTag`，同一标签内） | **已定为报错**（用户未另行反对，写入唯一规则稿）；**不得**默默用 id 排序次 | `A#2` 与 `B#2` 同标签 ⇒ **报错**（候选诊断码 `TAG_ORDER_DUP`，见 §0.8） |

## 1. 第一层｜现有真实诗：`古诗十九首/行行重行行.md`

### 1.1 源文件（`content/poems/古诗十九首/行行重行行.md`，完整原文）

```markdown
---
title: "行行重行行"
author: "佚名"
dynasty: "汉"
genre: "五言古诗"
orderInSource: 1
source: "《文选》卷二十九·杂诗上「古诗一十九首」（李善注本）。电子文本：汉典古籍 gj.zdic.net/jibu/1224/34173.html，2026-10-14 访问；以四库全书本《六臣注文选》卷二十九对校。异文校记见 docs/sources/gushi-shijiu-shou.md。"
---

行行重行行，与君生别离。
相去万余里，各在天一涯。
道路阻且长，会面安可知？
胡马依北风，越鸟巢南枝。
相去日已远，衣带日已缓。
浮云蔽白日，游子不顾反。
思君令人老，岁月忽已晚。
弃捐勿复道，努力加餐饭。

## 详情

### 异文

- **游子不顾返** —— 四库全书本《六臣注文选》卷二十九、《玉台新咏》卷一「枚乘杂诗」其三，此句均作「返」；底本（李善注本）作「反」。反、返古通用。
- **胡马嘶北风** —— 《玉台新咏》宋刻本作「嘶」，见清·纪容舒《玉台新咏考异》卷一（四库全书本）校语：「依，宋刻作嘶。按：此二句乃以一南一北申足『各天一涯』之意，以起下『相去日远』，作依为是。今从文选。」纪昀校正本《玉台新咏》卷一影印本同此校语；二手转录站古文岛亦作「嘶」。底本《文选》李善注本、四库全书本《六臣注文选》、明《诗纪》两刻本均作「依」；宋本影像本工作线未目验。
- **会面安可期** —— 明·冯惟讷《诗纪》卷二十（汉第十·古诗十九首）于「会面安可知」下出校语「一作期」，另一明刻本《诗纪》卷之十同；底本作「知」。
```

### 1.3 三个「看起来都像身份/次序」的东西，**互不等同**

| 东西 | 这一首里的值 | 它到底是什么 | 谁决定 | 改名会不会断 |
|---|---|---|---|---|
| **`id`** | `古诗十九首-行行重行行` | **身份**。由「相对 `content/poems/` 的完整相对路径、去 `.md`、`/`→`-`」**派生**（契约 §1「`id`」条）。目录名 `古诗十九首/` 只是**路径的一段**，它进 id 纯属路径拼接 | 磁盘上的文件名/目录名 | **会断**：改文件名/目录名 = 改 id（不做 `legacyId`、不做重定向，旧链接失效是已接受的代价） |
| **`source`** | `《文选》卷二十九…（李善注本）…` | **本仓采用的底本与出处**（校录所据的那一份），给「这首诗的正文是哪份文本」作证 | 内容线（人，可核） | 与选本归属**无关**：底本可以是《文选》，而归属可以是《古诗十九首》 |
| **`orderInSource`** | `1` | **本仓底本内的逐首次序**（在《文选》卷二十九里它排第 1） | 内容线（人，可核） | 与选本编次无关：选本（如《唐诗三百首》）有它自己的编次 |

三点补正，防止拿错：

- **目录不参与分组**。`古诗十九首/` 这个目录只是整理，分组权威是每首的 `dynasty`（这里 `汉`）＋ 顶层 `dynasties` 数组。⇒ **不能**「把目录名读成标签」。
- **`id` 里带着「古诗十九首」四个字，纯属路径巧合**：`古诗十九首/行行重行行.md` 拼出来的。若有人把诗挪到别的目录，id 会变，而「它属不属于《古诗十九首》」这个事实**不该跟着变** ⇒ 归属不能像 id 那样由路径承载。
- **`orderInSource` 是《文选》的次序，不是《古诗十九首》的次序**：这一首恰好两边都是 1，所以看着「一样」；这是**巧合，不是等式**（§2.8 正是要钉这一点）。

## 2. 第二层｜候选 frontmatter 写法（4 种，含 2 种否决）

### 2.1 先说编译器的三道门（实测，2026-10-18）

| 门 | 现状 | 实测输出 |
|---|---|---|
| front matter 键白名单 | 必填 `title/author/dynasty/source` ＋ 可选 `genre/orderInSource`；**新键 ⇒ 编译失败** | `[UNKNOWN_KEY] front matter 出现声明之外的键「tags」；允许的键：必填 title/author/dynasty/source，可选 genre/orderInSource` |
| YAML 子集 | **不支持行内 flow 集合**（`[a, b]`） | `[YAML_UNSUPPORTED] 不支持行内集合写法（请改用缩进列表，空数组写 []）：[古诗十九首]` |
| 节名 | 只认 `## 详情` / `## 笔记` | `[UNKNOWN_SECTION] 未知的节标题：`## 标签`（第 12 行）。本格式只认两个节…` |

⇒ 所以**任何**候选都必须先改契约与编译器；区别只在「改多少」。下面 4 种都按「假定白名单已放开」来评估形状，但**本期都没有放开**。

### 2.2 候选 P（**2026-10-18 已被用户采纳**）：front matter 缩进块序列，元素是对象（**中文 id ＋ 可选 orderInTag**）

**先厘清一件事：稳定标识 ≠ 必须 ASCII slug。** 稳定的是「**key**」，可变的是「**显示名**」——两者分开，**中文 key 完全成立**（用户现有内容 ID 本来就全是中文）：

| 子形态 | 源文件长什么样 | 改名时 | 代价 |
|---|---|---|---|
| **P1（中文稳定 key）** | `- 古诗十九首` | 改 `tags[].name`，源文件一字不动 | 与既有中文 ID 同风格、**源里直接可读**；key 需人手声明（标签没有路径可派生） |
| **P2（ASCII slug）** | `- gushi-shijiu-shou` | 同上 | 便于命令行/外部工具；源里不可读 |

两者**同构**（都是「稳定 key ＋ 可改显示名」），**不存在**「只有英文 key 成立、中文只能当可变名」的二选一。下面示例用 **P1 中文 key**；`tag-data-draft.json` 里用 slug 只是**其中一种实例**，不是唯一形状。

一首诗：一个标签。

```yaml
tags:
  - 古诗十九首
```

一首诗：两个标签，其中一个还带选本内次序（未知就写 `orderInTag: null` 或整项省略）；**换成 P2 的 slug 写法时形状完全相同**：

```yaml
tags:
  - id: 古诗十九首
    orderInTag: 1
  - id: 唐诗三百首（蘅塘退士本）
    orderInTag: 22
```

无标签（**合法状态**，明确写空列表，别靠「不写」）：

```yaml
tags: []
```

**为什么「能解析」不是空话**（实测 `parseFrontMatterLines` 的返回值）：

- `- 标量` 的块序列 ⇒ `{"tags":["古诗十九首","唐诗三百首"]}` ✅
- `- key: value` 的**对象项**块序列 ⇒ `{"tags":[{"name":"古诗十九首","order":3},…]}` ✅
- `tags: []` ⇒ `{"tags":[]}` ✅；`tags:`（空值）⇒ `{"tags":null}` ⚠（与 `[]` **不同**，要定死用哪个）
- `tags: [a, b]` ⇒ `YAML_UNSUPPORTED` ❌
- 顶层 `# 整行注释` ✅，但**序列里不能放注释**：`  # 古诗十九首` ⇒ `YAML_UNSUPPORTED`；**行尾注释会被静默吞进值**：`- 古诗十九首  # 选本` ⇒ `{"tags":["古诗十九首  # 选本"]}` ⚠⚠（**这条很重要**：候选 P 的写法**没法**在源文件里就地加小注）

⚠ **这是「当前解析器的成本」，不是「用户否定了注释」**：把注释支持当需求是另一件事（解析器演进，候选、未排期）。而且选 **P1 中文 key** 时源里本身就已是可读的中文，这条成本也随之明显变小。

⇒ 候选 P **现在就能解析**（缩进块序列已支持），只需把 `tags` 加进键白名单 ＋ 加校验与产物组装。**但这不构成推荐它的主要理由**（权重见 §2.6 末尾）。

### 2.3 候选 N：front matter 缩进块序列，元素是**中文显示名**

```yaml
tags:
  - 古诗十九首
  - 唐诗三百首   # ← 注意：行尾注释会被吞进名字里，所以连这个都不能写
```

显示名要靠一张 registry（`name` + `aliases`）解析成 id。看起来最好读，但：

- 同名不同选本（语义 §2.5）⇒ 名字**不是唯一键**，必须再定一条消歧规则（歧义 ⇒ 编译报错要求改用 id 写法）；
- 改名（语义 §2.6）⇒ 旧名必须留成 `aliases`，否则所有源文件一起断；`aliases` 只增不减会慢慢长出「名字考古层」。

### 2.4 候选 S：单独一节 `## 标签`

```markdown
## 标签

- 古诗十九首
- 唐诗三百首
```

- 现状：`## 标签` ⇒ `UNKNOWN_SECTION`（实测，见 §2.1）。
- 要落地得改：`tools/lib/interface.mjs` 的 `KNOWN_SECTIONS = ['详情','笔记']`（**只在编译器里用**——`content-build.mjs:278`）＋ 契约 §1「正文之后只认两个节」这条口径要放宽。
- ⚠ **两端不需要「节名清单」**（已核源码）：`web/` 与 `android/app/src/main` **没有任何 `KNOWN_SECTIONS` 引用**，客户端只吃 `content.json`。只要编译器把这一节提取成与 front matter **同形**的 JSON，客户端根本不知道源里写的是节还是 front matter。
- 更麻烦的是**机器可读性**：节体是「最小 Markdown 文本」，`- 古诗十九首` 的列表项、裸行、`**古诗十九首**`、甚至 `1. 古诗十九首` 都能出现在合法文本里 ⇒ 要定一套「这一节必须只有列表项」的额外语法约束，否则歧义面比 YAML 更大。
- 选本内次序（§2.8）在节里只能发明微语法（`- 古诗十九首 @22`），等于**自己再造一个解析器**。

### 2.5 不成立的写法（按**当前**解析器与契约；**不是用户的永久否决**）

> 读法：每条都写清「**现在为什么不行**」。`[a, b]` 行内集合、注释这类属于**解析器现状**，将来做解析器演进时可以重新评估——**不要把它们读成用户已经否掉的东西**。

| 写法 | 为什么否决 |
|---|---|
| `tags: [古诗十九首, 唐诗三百首]`（行内集合） | 现解析器直接 `YAML_UNSUPPORTED`；契约 §1.1 明写不支持 flow 集合 |
| `tag: 古诗十九首`（单标量） | 表达不了多标签（§2.2）；要表达就得写逗号串 ⇒ 名字里出现分隔符即歧义 |
| `tags: 古诗十九首,唐诗三百首`（逗号串） | 同上，且「唐诗三百首，卷一」这种名字无法表达 |
| 把标签编进目录或文件名（`content/poems/古诗十九首/唐诗三百首/行行重行行.md`） | 直接改 **ID**（语义相反：改归属就改身份）；且「同时属两个选本」只能靠复制作品 —— **明令禁止** |
| 在 `source` 里写「（收录于《古诗十九首》）」 | 把底本与归属混成一栏，`source` 语义被改写 —— **明令禁止** |
| 用 `orderInSource` 兼作选本次序 | §2.8 正面反例：底本次序 ≠ 选本编次 |
| `_tags.md` / `README-tags.md` 当标签清单 | 扫描阶段 `_` 前缀与 `README*` 都**静默忽略并计数**（`ignoredReason`），当清单用就是「看起来有保障、其实没有」 |
| 为标签建目录 `content/tags/<id>/` | 明令禁止；标签没有路径，也不需要 |

### 2.6 逐项对比表

| 维度 | **候选 P**（frontmatter，记 id） | 候选 N（frontmatter，记中文名） | 候选 S（`## 标签` 节） | 否决：目录/文件名 |
|---|---|---|---|---|
| **人读可读性** | **P1 中文 key：高**（源里就是中文）；P2 slug：中（不可读，**且无法加行尾/缩进注释**——实测被吞/报错） | **高**：源文件里就是中文（但名字与身份绑死，见「改名代价」行） | 高：与 `## 详情`/`## 笔记` 同构，写在正文之后 | 高（一眼看到选本名） |
| **与既有 frontmatter 子集的相容性** | **已可解析**（缩进块序列/对象项都支持）⇒ 只需加白名单 | 已可解析，但要加「名字→id」解析层 | 变更最大：新增节名（契约 §1 ＋ **编译器**的 `KNOWN_SECTIONS`），还要收严节内语法；**两端不受影响**（只吃 JSON，已核） | 相关为 0（不进 front matter），但撞 ID 与复制作品两条硬约束 |
| **改名代价**（§2.6） | **0 处源改**：改 registry 里的 `name`，诗的 `tagId` 不动 | 每首源文件都要改；除非 registry 留 `aliases`（=把改名代价换成别名考古） | 同候选 N（若节里写的是中文名）；若节里写 id，则等同候选 P 但可读性优势也没了 | 改名 = 改目录 = 改 **ID**（不可接受） |
| **增删代价**（§2.7） | 加选本：registry 加一条；诗入/出选本：改那一首的一行（git diff 局部、可审） | 同，但入/出要写中文名，重名时必须补消歧 | 同，但一次要动「正文之后的节」结构，diff 位置离 front matter 远 | 加选本 = 建目录；入/出 = 移动文件 = 改 ID |
| **对 `content/poems/**` 路径与 ID 的影响** | **零**：不改路径，不建目录，不复制文件 | **零** | **零** | **直接破坏**（ID 由路径派生） |
| **同一次序是否能表达**（§2.8/2.9） | 能：`orderInTag` 与 `orderInSource` 并列、互不顶替 | 要另配一行，仍能，但更绕 | 需自造微语法 | 只能塞进路径 ⇒ 破坏 ID |
| **同上限/排序等未定项** | 不设上限；层级顺序 = 源里的书写顺序 | 同 | 同，但「书写顺序」在 Markdown 列表里更容易被误改 | — |
| **编译期要新增的工作** | 白名单 + `tags` 校验（id 必须在 registry 里）+ registry 读取 + 产物组装 | 上面那些 **再加上**名字解析/歧义报错/别名 | 上面那些 **再加上** 节解析器与节内语法 | — |

**推荐：候选 P（P1 中文 key 或 P2 slug 皆可）。** 理由按权重：① **改名零源改、同名不同选本天然可分**——这两条是语义 §2 的硬边界，**这才是真正的理由**；② 增删是「一首诗一行」的局部 diff，可审；③ 对路径/ID 零影响；④ 解析器**现在**就能解析这个形状（**这是当前成本低，不是否定其它写法的依据**）。
**代价（诚实说）**：P2 slug 在源里不可读、且**没地方就地加小注**（实测行尾注释会被吞进值）——选 P1 中文 key 可把这条成本降到很小。
⚠ **不要用「把标签说明塞进诗的 `## 详情` 正文」来补可读性**：`## 详情` 是**诗的内容**（会进产物、会公开显示），往里写编辑备忘就是**内容污染**。标签的说明应放在**标签表侧的说明字段**（候选，未定），或源文件的**非产物**位置。

## 3. 第三层｜完整 JSON 形状（产物）

### 3.1 归属怎么落：**「全局标签表 ＋ 诗上引用」（两者）**

- **顶层 `tags[]`**：标签的**身份与显示名**（`id` / `name` / `qualifier`）＋ **编译期派生的 `members[]`**（该选本在本库收录的诗 id，**已按选本编次排好**）。
- **诗上 `poems[].tags[]`**：**归属事实的唯一人手来源**（`tagId` ＋ `orderInTag`）。
- 关系：`tags[].members` **由** `poems[].tags` **编译期生成**。⚠ **这只是「约束」，不是「结构保证」**：JSON 本身并不禁止两处不同 ⇒ **必须**在构建里加一条**一致性断言**（双向互查：每条 member 都能在该诗上找到对应 tagId；每条诗上的 tagId 都出现在 members 里、次序符合 `orderInTag`）。不加断言，「一致」就是我们要来的，不是白得的。

**最小产物形态先摆清楚**（下面两句均为**草案取舍、未采纳**）：只有诗侧 **`poems[].tags[]`**（`tagId` ＋ `orderInTag`）也能工作——不输出顶层标签表、不输出派生索引是合法的最小形态。**顶层表分两种，别混**：① **源侧定义表**（人手写，决定“有哪些标签”）；② **产侧派生表/有序索引**（编译期生成，按既有「编译期是唯一排序权威」）。现草案的 `tags[]` 是②；若哪天需要①，最小是 `[{ "id": "古诗十九首" }]`（中文 id 即显示名，**不强制 `name`**）。

为什么不全放诗上（诗上只写 key、不写显示名）：**显示名只存一处** ⇒ 改名不改任何源文件（§2.6 的核心目标）。

**`members` 不是唯一形态**——下面是并列候选，**不要**把「保留 members」当成「避免破坏既有排序口径」的唯一道路：

| 候选 | 形状 | 好处 | 代价 |
|---|---|---|---|
| **M-a `members[]`** | `tags[].members: ["行行重行行", …]`（有序 id） | 一次取全、次序已排好 | 产物多 2 条路径（`tags[].members`、`tags[].members[]`）＋需一致性断言 |
| **M-b `orderedPoemIds[]`** | 同上但**只放 id**（不重复任何诗字段） | 与 M-a 等价、命名更诚实（「这是编译期派生的序列」） | 名字决定读者会不会误以为是第二事实源 |
| **M-c 不输出索引** | 产物只有诗侧 `poems[].tags[]` | 产物最小、无一致性风险 | 客户端要自己按 `orderInTag` 过滤+排序 ⇒ 撞既有口径「**编译期是唯一排序权威，客户端不得重排**」（`docs/design/content-contract.md` §174）——要么放宽它（需用户拍板），要么编译期另出「已排好的 id 序列」，那其实回到 M-a/M-b |

### 3.2 稳定 ID 与显示名分开

| 字段 | 语义 | 可变性 | 约束 |
|---|---|---|---|
| `tags[].id` | 标签**身份**（key），诗的引用只认它 | **永不变**（改名不改它） | **中文 key（如 `古诗十九首`）或 ASCII slug 均可**——稳定的是「它不变」，**不是「它必须 ASCII」**；优先与用户现有中文 ID 同风格；全局唯一（同 `id` 口径：NFC ＋ 大小写折叠后不准撞）；**不由路径派生**（标签没有目录 ⇒ 只能人手声明） |
| `tags[].name` | **显示名** | 随改随生效，不影响任何归属 | 非空；**允许重名**（同名不同选本就是两条 tag，见 §3.3 形态三） |
| `tags[].qualifier` | 可选限定语（编者/版本/说明），界面消歧用 | 可变 | `null` 或非空字符串；**怎么用未定**（语义 §2.5 明确「要不要加限定、加在哪儿，未定」） |

### 3.3 三种形态的完整 JSON 片段（均摘自 [`tag-data-draft.json`](tag-data-draft.json)，示例数据）

**形态一｜无标签（语义 §2.3：合法状态，诗照旧在 `poems` 里、目录照旧能列出）**

```json
{
  "id": "毛泽东-七律·和郭沫若同志",
  "title": "七律·和郭沫若同志",
  "author": "毛泽东",
  "dynasty": "近现代",
  "genre": "七言律诗",
  "source": "毛泽东诗词全集",
  "orderInSource": null,
  "tags": [],
  "detail": null,
  "stanzas": [["一从大地起风雷，便有精生白骨堆。", "…"]],
  "notes": null
}
```

（`tags: []` 而非 `null`：**「不属于任何选本」是一个真实的、可以显示的状态**，与 `notes: null`（没有笔记文本）不是一回事；且空数组在字段集口径下照样登记 `poems[].tags` / `poems[].tags[]` 两条路径，形状恒定。）

**形态二｜多标签（语义 §2.2：作品只有一条，绝不复制）**

诗侧（**归属的唯一人手来源**）：

```json
"tags": [
  { "tagId": "tang-sanbai-shou-hengtang", "orderInTag": 22 },
  { "tagId": "tang-sanbai-shou-other", "orderInTag": null }
]
```

标签侧（**编译期派生**，`members` 已排好序；`orderInTag: null` 的排在有值之后）：

```json
{
  "id": "tang-sanbai-shou-hengtang",
  "name": "唐诗三百首",
  "qualifier": "清·蘅塘退士编（示例归属，未核）",
  "members": ["杜甫-梦李白二首·其一"]
}
```

同一首诗**只出现一次**在 `poems` 里，`stanzas` 只有一份 ⇒ 「两个标签 ⇒ 两个作品」这件事在结构上做不到。

**形态三｜同名不同选本（语义 §2.5）**

```json
"tags": [
  { "id": "tang-sanbai-shou-hengtang", "name": "唐诗三百首", "qualifier": "清·蘅塘退士编（示例归属，未核）", "members": ["杜甫-梦李白二首·其一"] },
  { "id": "tang-sanbai-shou-other", "name": "唐诗三百首", "qualifier": "同名异版（示例…）", "members": ["杜甫-梦李白二首·其一"] }
]
```

两个 `name` 完全相同、`id` 不同 ⇒ **唯一定位靠 `id`**，界面靠 `qualifier` 消歧。这正是「不能只靠名字唯一定位」的可实现形式。

### 3.4 键位与空值约定（候选，采纳时须一次定死）

- 顶层键序：`formatVersion`、`contentVersion`、`generatedAt`、`dynasties`、**`tags`**、`poems`（`tags` 插在 `dynasties` 之后、`poems` 之前：先分组轴、再归属轴、最后作品）。
- 诗键序（10 → 11 键）：`id`、`title`、`author`、`dynasty`、`genre`、`source`、`orderInSource`、**`tags`**、`detail`、`stanzas`、`notes`。
- 空值：`poems[].tags` 空 ⇒ `[]`；`tags[]` 空 ⇒ `[]`；`poems[].tags[].orderInTag` 未知 ⇒ `null`（**键仍在**，与 `orderInSource` 同一约定）；`tags[].qualifier` 无 ⇒ `null`。
- `orderInTag`：`null` 或 ≥ 1 的整数；**不是** `orderInSource` 的别名，两者**同时存在、各自独立**（语义 §2.9）。

## 5. 对照表：字段 → 语义 → 反例

反例一律取自 [`tag-semantics` §2](../../tag-semantics/item.md)。

| 字段 | 语义（一句话） | 反例（错在哪） |
|---|---|---|
| `tags[].id` | 标签的**稳定身份**，诗的引用只认它；改名不动 | 「把显示名当唯一键」⇒ 把《唐诗三百首》改成《唐诗三百首（补注本）》时，诗的归属全断（违反 §2.6） |
| `tags[].name` | **显示名**，可改、可重名 | 「靠 name 唯一定位」⇒ 两条同名不同选本的《唐诗三百首》在界面上分不开（违反 §2.5） |
| `tags[].qualifier` | 可选限定（编者/版本），只用于消歧**显示** | 「把限定语拼进 name 当唯一名」⇒ 名字变成事实断言（如把「清·蘅塘退士编」写成 name），改名又回到「改 N 处」 |
| `tags[].members[]` | 该标签在本库**已收录**的诗 id（**派生**、已排序） | 「把 members 长度当成选本总篇数」⇒ 界面写成「唐诗三百首（300 首）已全部收录」，而我们只收了 N 首（违反 §2.4） |
| `poems[].tags[].tagId` | 这一首**归属**哪个标签（归属的唯一人手来源） | 「为两个标签复制两个作品」⇒ 同一首诗出现两条 `poems`、正文两份、改一处漏一处（违反 §2.2）；「把唐诗三百首自动套给所有 `dynasty: 唐` 的诗」⇒ 没被该选本收的也进了（违反 §2.4） |
| `poems[].tags[].orderInTag` | **选本内编次**（该选本自己第几首） | 「用 `orderInSource` 顶替」⇒ 底本《文选》的次序冒充《唐诗三百首》的编次，两边不一致时就在撒谎（违反 §2.8/2.9） |
| `poems[].orderInSource` | **本仓底本内的逐首次序**，语义**不变** | 「为标签改写它」⇒ 底本次序被归属污染，`--order source` 的组内排序跟着错 |
| `poems[].source` | 本仓**采用的底本/出处**，语义**不变** | 「把选本写进 source」⇒ 底本与归属混成一栏；《全唐诗》作底本、《唐诗三百首》作归属这种真实情形再也表达不了 |
| `poems[].dynasty`（**不动**） | **分组轴**（汉/唐/近现代…），一个中文组名，精确匹配顶层 `dynasties` | 「把『唐诗三百首』当朝代」⇒ `dynasty` 变成标签，`唐` 这一组的语义被抹掉，且一首诗只有一个 dynasty、装不下两个标签（违反 §2.1/§2.2） |
| `poems[].genre`（**不动**） | **体裁**（五言古诗…），形式属性 | 「把体裁当标签」⇒ 同一首五言古诗被强行归入某个「体裁集合」，与被哪个选本收无关（§1 表格） |
| `poems[].id`（**不动**） | 路径派生的**身份** | 「用目录承载标签」⇒ 改归属就是改 id，旧链接全断；「同时属两个选本」只能复制作品（**明令禁止**） |
| `dynasties`（**不动**） | 顶层**有序中文值数组**，分组权威 | 「在 dynasties 里混入选本名」⇒ 目录默认视图把选本当朝代列出来（违反「朝代分组必须保持可用」） |
| **不存在的字段**：`tags[].total` / `totalInEdition` | 选本**总篇数**（本候选**没有**加） | 「用『本库已收 N 首』暗示选本只有 N 首」（违反 §2.4）——若要正面表达「收录 N / 选本共 M」，需要**新增**字段（未定，见 §6.2） |

## 6. 必答：这份候选能表达语义 §2 的哪几条

### 6.1 能表达（9 条：2.1–2.9）

| §2 例子 | 怎么表达 | 备注 |
|---|---|---|
| **2.1 一首诗一个标签** | `poems[].tags` 只有一个元素；`tagId` 指向《古诗十九首》 | 且明确**不是** `dynasty: 汉`、不是 `genre: 五言古诗`、不是 `source`、不是目录名 |
| **2.2 一首诗多个标签，作品只一条** | `poems[].tags` 多元素；诗只出现一次；`stanzas` 只有一份 | 结构上**做不出**「复制作品」这一步 |
| **2.3 无标签是合法状态** | `tags: []`；诗仍在 `poems` 里，目录仍列出 | 不因「没有标签」而隐藏；空数组不是 `null`（见 §3.3 形态一） |
| **2.4「唐诗三百首」不能自动套给所有唐诗** | 归属是**逐诗声明**的，没有任何「按 dynasty 推导标签」的规则；`members` 只含被声明的诗 | 数据侧不阻碍；**但「不能写成 300 首已全部收录」是 UI 文案约束，不是字段能强制的**（见 6.2） |
| **2.5 同名不同选本不能只靠名字定位** | 两条 `tags` 同 `name`、不同 `id`；诗用 `tagId` 引用；`qualifier` 供消歧 | 「限定怎么加」仍**未定**：本候选只留 `qualifier` 占位，不定取值与显示规则 |
| **2.6 标签改名不丢归属** | 改名只改 `tags[].name`，`poems[].tags[].tagId` 一字不动 | 这正是选「候选 P 记 id」而不是「记中文名」的核心理由 |
| **2.7 标签增/删** | 加选本 ⇒ `tags[]` 加一条；入/出选本 ⇒ 改那一首的 `tags`；诗的正文不动 | 删到空 ⇒ `tags: []`，诗仍在 |
| **2.8 选本内次序 ≠ `orderInSource`** | `poems[].tags[].orderInTag` 与 `poems[].orderInSource` **两个字段并存** | 二者可同时有值、可互相矛盾（矛盾是真实的，不是错误） |
| **2.9 同一首诗两个「次序」同时存在** | 同上一行（§2.9 是 §2.8 的正面情形） | 分开存 ⇒ 谁也不能顶替谁 |

### 6.2 表达**不**了的 / 只能算「不阻碍」的（如实）

| 项 | 状态 |
|---|---|
| **§2.4 的「本库已收 N」** | **已可表达**：`tags[].members.length`（或诗侧计数）就是「本库已收录 N 首」，不需要新字段。 |
| **§2.4 的「选本共 M」** | **不是已确认的需求**：用户从未要求表达 M。本候选**不提供**该字段，**也不让用户为此挑新字段**；若将来用户明确提出，再评估（候选名可留 `totalInEdition`，现在不设计、不加约束）。 |
| **§2.5 的「限定加在哪、怎么加」** | **只给了位置，没给规则**。`qualifier` 是字符串，谁写、写什么格式、界面怎么拼，**都未定**。 |
| **§2.10 主题/作者等其它轴** | **不阻碍，但不算表达**：结构里**没有**任何「仅 collection-only」的写死（tag 对象只有 id/name/qualifier/members，没有 kind 枚举），所以将来加主题标签不必改形状；但**取值、筛选行为、是否自动扩库全未定**，本期不定义、也不据此扩库。 |
| **标签列表本身的显示次序** | **未定**：本候选建议 `tags[]` 数组次序 = registry 里的声明次序（人选）；若将来要「按收录数排」，要么编译期算、要么客户端排（客户端重排与「编译期唯一权威」口径冲突，需要一次决定）。 |
